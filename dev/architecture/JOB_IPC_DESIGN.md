# ジョブマネージャーに問い合わせる口の設計

CAD/CAM のアプリが、ジョブの保存先のファイルを直接読み書きせずに、ジョブマネージャーに問い合わせて投入・状態の読み取り・成果物の取り込みを行うための口（プロセスの間の通信）を決める（#1183）。

## 1. 背景

- 前は、アプリがジョブの保存先のフォルダに投入を書き、ジョブの記録と成果物のファイルを直接読んでいた（`JOB_MANAGER_STORAGE_DESIGN.md` 4 章）。保存先の場所は、ジョブマネージャーが書く所在のファイルで知っていた（#1178。口に替えて消した）
- この形では、アプリが保存先のファイルの配置と形式に依存する
  - 保存先の形式を変えると、アプリも合わせて変える必要がある
  - ジョブマネージャーを別の PC に置けない
  - 保存先を替える瞬間に、アプリが前の保存先に書いている途中の投入は、前の保存先に残る
- アプリの投入・取り込みは、すでに境界（`application::job_client::JobClient`）の後ろにある。口を使う実装を足し、境界から上（ワークフロー・ViewModel）は変えない

## 2. 方針

- ジョブマネージャーが、利用者ごとの口で要求を受ける。Windows では名前付きパイプ、ほかの OS では UNIX ドメインソケットとする
- 口は、同じ PC の同じ利用者だけが使える（3 章）。別の PC からの接続（リモートのジョブマネージャー）は、この設計の範囲の外とする（認証・通信の暗号化を、別の Issue で決める）
- 入力と成果物の中身も、口で小分けにして送る（アプリは保存先のパスを知らない。後でリモートに広げるときも、同じ要求を使える）
- 口の操作は、CAM に依らない（ジョブの種類・状態・投入元と、決まった名前のファイルの中身だけを扱う）。入力・成果物のバイナリの読み書き（`cam_sim` の形式）は、今と同じくアプリの側で行う
- 投入は、ジョブマネージャーが受付のフォルダに書く（取り込み・ランナーの起動の仕組みは変えない）

### 2.1 クレート

- 新しいクレート `job_ipc` を Model の層に置く。要求・応答の型、送り方（枠）、口の開き方・つなぎ方を持つ
- `job_ipc` は、ほかのワークスペースのクレートに依存しない（保存先の形式と口の形式を分ける。口の型は、ジョブの記録の型を写さず、自分で持つ）
- アプリ（`application`）は口のクライアントとして、ジョブマネージャーの実行ファイル（`job_manager_app`）は口の受け手として、`job_ipc` に依存する。依存関係の決まり（`scripts/_arch_rules_data.ps1`）に足す

## 3. 口の安全

### 3.1 Windows（名前付きパイプ）

- 名前は `\\.\pipe\RedRing.JobManager.<利用者の SID>` とする（利用者ごとに 1 つ）
- ジョブマネージャーは、パイプを次のとおりに作る
  - セキュリティ記述子で、接続できるのを、その利用者だけにする（`SYSTEM` と管理者のグループにも渡さない）
  - `FILE_FLAG_FIRST_PIPE_INSTANCE` で最初のインスタンスを作る（ほかのプロセスが先に同じ名前のパイプを作っていれば、作れずに口を開かない）
  - `PIPE_REJECT_REMOTE_CLIENTS` で、ネットワークからの接続を拒む
- アプリは、つないだパイプの持ち主（所有者の SID）が自分であることを確かめてから要求を送る（ほかの利用者が先に作ったパイプに、入力を送らない）
- パイプを作るのは、設定の保存先を開いたジョブマネージャーだけとする（試しに `--store` で別の保存先を指定して起動したジョブマネージャーは、口を開かない）

### 3.2 ほかの OS（UNIX ドメインソケット）

- `$XDG_RUNTIME_DIR/redring/job-manager.sock`（`XDG_RUNTIME_DIR` がなければ口を開かない）に置く。フォルダは 0700、ソケットは 0600 とする
- アプリは、ソケットの持ち主が自分であることを確かめる

### 3.3 要求の大きさ

- 要求の JSON は 1 つ 64 KiB まで、応答の JSON は 1 つ 16 MiB まで（ジョブの一覧を 1 つの応答で返すため。1 つのジョブは 250 バイトほどで、6 万件ほどまで返せる）
- 送る中身の小分けは 1 つ 1 MiB まで。中身の合計は、投入の入力は合わせて 1 GiB まで（ジョブマネージャーは、入力をすべて受け取ってから受付のフォルダに書くため）、成果物は 1 つ 4 GiB まで
- 上限を超えたら、その接続を切る（読みかけの投入は受付のフォルダに残さない）
- ジョブマネージャーが同時に受ける接続は 4 つまでとする（Windows では、5 つ目のつなぐ側は空くまで待つ。ほかの OS では、受けてすぐに閉じる）

## 4. 送り方

### 4.1 枠

接続の上を、枠の並びで送る。枠は、種類（1 バイト）・長さ（4 バイト、リトルエンディアン）・中身とする。

| 種類 | 中身 |
|---|---|
| 0: JSON | 要求・応答（UTF-8 の JSON。3.3 の上限） |
| 1: 中身 | 送る中身の小分け（3.3 の上限） |
| 2: 中身の終わり | なし（その中身を送り終えた） |

中身を送る要求・応答は、JSON の枠に中身の名前と大きさを書き、続けて中身の枠を送り、中身の終わりの枠で閉じる。大きさと受け取った長さが違えば、誤りとして接続を切る。

### 4.2 版

- 接続したら、アプリは最初に `hello`（口の版）を送り、ジョブマネージャーは `hello`（口の版と、ジョブマネージャーの版）を返す
- 口の版が違えば、ジョブマネージャーは誤り（`unsupported_version`）を返して接続を切る。アプリとジョブマネージャーは同じ配布物に入れるため、版が違うのは、古いジョブマネージャーが動き続けているときだけである。アプリは、ジョブマネージャーを起動し直すように出す
- 1 つの接続で、要求と応答を順に何度も行える（1 つの要求に 1 つの応答。並べて送らない）

## 5. 操作

`JobClient` の操作を、次の要求で行う。

| 要求 | 応答 | `JobClient` の操作 |
|---|---|---|
| `submit`（ジョブの列: 種類・入力のファイルの名前・依存・優先順位・投入元・入力の CL のファイルの名前。続けて入力の中身） | `submitted`（投入の ID） | `submit`・`submit_simulation` |
| `jobs` | `jobs`（ジョブの番号・種類・状態・依存するジョブ・投入の ID・投入元・入力の CL を持つか・成果物があるか） | `toolpath_jobs`・`simulation_jobs` |
| `pending_submissions` | `pending_submissions`（投入元・取り込めなかったか） | `pending_submissions` |
| `read_job_file`（ジョブの番号・ファイル: 入力・入力の CL・成果物） | `job_file`（大きさ。続けて中身） | `import` |
| `open_window` | `ok` | `open_manager_window` |

- ウィンドウを前に出す権利は、利用者が操作しているアプリの側にある。Windows では、アプリが `open_window` を送る前に、パイプの相手のプロセス（`GetNamedPipeServerProcessId`）に前に出す権利を渡す（PR 3）

- 誤りは、`error`（種類と英語の詳しい理由）で返す。種類は、正しくない要求・版の違い・ないジョブ・ないファイル・保存先を読み書きできない・上限を超えた、とする
- 投入の ID はジョブマネージャーが作る（今はアプリが作っている）。ジョブの番号は、取り込みの後に決まるため、投入の応答には入れない（今と同じく、投入の ID と投入元でジョブを引く）
- 取り込み（`import`）は、アプリが `jobs` で状態を確かめてから、`read_job_file` で入力と成果物を読む。間でジョブが消されたら、ないジョブ・ないファイルの誤りになる
- `read_job_file` で読めるのは、ジョブのフォルダの決まった名前のファイルだけとする（今の取り込みと同じく、記録の参照からパスを作らない）
- 取り込んだ結果をジョブマネージャーに伝える要求（ジョブマネージャーの「まとめて削除」で、取り込み済みの CL の元を消せるように。#1157）は、口ができた後に足す

## 6. 起動と接続

- アプリは、口につなげなければ、自分と同じフォルダのジョブマネージャーを、ウィンドウを出さずに起動し、口が開くまで待ってつなぐ（待つのは 5 秒まで。保存先のロックを確かめたり、`--store` を渡したりしない）。状態を読むときも同じで、加工条件のウィンドウを開いている間は、止めたジョブマネージャーも起動し直す。起動してから 10 秒の間は起動し直さず、待たずに誤りにする（起動してすぐに終わるときに、操作のたびに起動して画面を止めないように）
- アプリは、操作ごとに接続をつなぎ直す（ジョブマネージャーを起動し直した・保存先を替えた後も、そのまま使える。同じ要求を 2 度送らない）
- 受け手（`job_manager::start_endpoint_server`）は、ジョブマネージャーのサービスのクレートに置く（アプリの境界の試験から、同じ受け手を使うため）
- ジョブマネージャーが保存先を替えるとき（`JOB_MANAGER_STORAGE_DESIGN.md` 4.1）は、前のプロセスを終えて口を閉じ、新しいプロセスが口を開く（新しいプロセスは、前のプロセスが口を閉じるまで、15 秒まで開き直す）。アプリは、つなぎ直すだけで新しい保存先を使う。書いている途中の投入は、口が閉じて誤りになる（前の保存先に残らない。アプリは投入をやり直せる）
- ジョブマネージャーの受け手は、別のスレッドで接続を受け、接続ごとのスレッドで要求を処理する
  - 状態と成果物は、保存先から読む（記録を書くのはサービスのスレッドだけ、の決まりは変えない）
  - 投入は、受付のフォルダに書く
  - ウィンドウを開く要求は、トレイと同じ仕組みでウィンドウを開く

## 7. 移行

| PR | 内容 |
|---|---|
| 1 | この設計の文書 |
| 2 | `job_ipc`（型・枠・口）と、ジョブマネージャーの受け手。依存関係の決まりに `job_ipc` を足す。アプリはまだ今の方式を使う |
| 3 | アプリの境界の実装を、口を使うものに替える。保存先のフォルダを通す今の実装（`LocalStoreJobClient`）と所在のファイルは消す |

- アプリとジョブマネージャーは同じ配布物に入れて替えるため、両方の方式を並べて使う期間は設けない（古いジョブマネージャーが動き続けているときは、4.2 の版の違いで分かる）
- 所在のファイル（`job_store_location.json`）は、PR 3 でアプリが読まなくなったら、ジョブマネージャーも書かない

## 8. 試験

- 枠と要求・応答は、メモリの上の読み書きで試験する（上限・版の違い・途中で切れた接続を含む）
- 口の試験は、試験ごとの名前の口（`Endpoint::with_name`。Windows ではパイプの名前に利用者の SID と試験の名前を入れ、ほかの OS では一時のフォルダに置く）を使う（利用者の実際の口・保存先には触れない）
- アプリの境界の試験は、試験ごとの保存先で動かした受け手につないで行う（今の `LocalStoreJobClient` の試験を写す）
