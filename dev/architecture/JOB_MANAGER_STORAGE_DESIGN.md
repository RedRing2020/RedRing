# ジョブマネージャーの保存先 設計書

**作成日**: 2026年11月5日
**ステータス**: 設計中
**関連Issue**: #914（本書）, #988, #1068, #932, #933, #1083, #1235

---

## 1. 目的

ジョブのキュー・状態・入力・成果物を、CAD/CAM のアプリのプロセスの外に置き、別の実行ファイルのジョブマネージャーが管理する。CAD/CAM のアプリを閉じていても、時間のかかる CAM の計算を続けられるようにする（`CAM_OPERATION_UI_DESIGN.md` 3.6）。

## 2. 背景

- 今は、ジョブのキューと状態（`job_runtime::JobManager`）、入力の登録先（`InMemoryCamSolverInputStore`・`InMemoryCuttingSimulationInputStore`）、成果物（ジョブの記録の成果物の履歴のバイト列）が、どれも CAD/CAM のアプリのプロセスのメモリの中にある。実行も同じプロセスの中で行い、実行中は画面が止まる
- ジョブマネージャーは、別の実行ファイルとし、1 つの PC に 1 つだけ起動し、タスクトレイに常駐する。OS の起動のときに自動で起動するオプションを持ち、CAD/CAM のアプリは投入のときに起動しているかを確かめ、起動していなければ起動する（`CAM_OPERATION_UI_DESIGN.md` 3.7）
- ジョブは、投入元（工程の ID と改訂の番号・改訂の鍵）を持つ（#1050・#1165）

## 3. 構成

| プロセス | 役割 |
|---|---|
| CAD/CAM のアプリ | 空間モデル・加工手順・加工工程を持つ。工程から投入し、ジョブの状態を読み、成果物を取り込む |
| ジョブマネージャー | ジョブのキューと状態を持ち、ジョブごとにランナーを起動して実行する。ジョブの記録を書くのはジョブマネージャーだけとする |
| ランナー | ジョブ 1 つの計算だけを行う実行ファイル。ジョブごとに別のプロセスとして起動する |

- ランナーの引数は、今の Docker のランナーの形（`--job-type`・`--input`・`--output`・`--logs`。`scripts/batch_runner_stub.sh`、`BATCH_COMPUTE_PLATFORM_DESIGN.md` 16 章）にそろえる。同じランナーを、Docker・K8s のバッチでもそのまま使う
- ジョブごとに別のプロセスにする理由: 計算が落ちてもジョブマネージャーは落ちない。取り消しは、ランナーのプロセスを止めるだけで済み、計算の中で中断の要求を確かめる仕組みが要らない

### 3.1 ランナーの実行ファイル（#1076）

ランナーは `job_runner` のクレートの実行ファイル `redring-batch-runner` とする。

```text
redring-batch-runner --job-type cam --input <入力> --output <フォルダ> --logs <フォルダ> [--progress <ファイル>]
                     [--resume <ファイル>]
redring-batch-runner --job-type sim --input <入力> --toolpath <ツールパスの成果物> --output <フォルダ> --logs <フォルダ>
                     [--progress <ファイル>]
```

- `--input` はジョブの入力のファイル（5.2）。切削シミュレーションは、親の CAM の計算のジョブのツールパスの成果物を `--toolpath` で受け取る（Docker のランナーの引数に 1 つ足す。区間の終わりの素材の受け渡し（5.4）も、同じ形で引数を足す）
- 成果物は、出力のフォルダに `toolpath.bin`（CAM の計算）・`cutting_simulation.bin`（切削シミュレーション）の名前で書く。ログは、ログのフォルダの `runner.log`（英語）に書く。書いている間は `runner.log.tmp` で、終わったら名前を変える（ランナーが落ちた場合は、`runner.log.tmp` に途中までのログが残る）。ランナーの標準エラー出力は、ジョブマネージャーがログのフォルダの `runner.stderr.log` に残す（メモリを確保できずに止まった・panic など、ランナーがログに理由を書けないときの理由。#1233）
- 進み具合は、`--progress` を指定した場合に書く（`{"state":"running"|"succeeded"|"failed","fraction":0.0〜1.0}`）。今は始まり（0）と終わり（1）だけを書き、計算の途中の割合は、計算の側に進み具合を返す仕組みを足すときに書く
- 成果物・進み具合は、一時の名前（`*.tmp`）で書き終えてから名前を変える（4.2）
- `--resume` は、ツールパス生成の途中の結果のファイル（3.3）。あって使えるときは続きから計算し、ないか使えないときは最初から計算して、終えた区切りを書き足していく
- 終了の番号

  | 番号 | 意味 |
  |---|---|
  | 0 | 正常に終わった |
  | 2 | 引数の誤り |
  | 3 | 入力のファイル（`--input`・`--toolpath`）を読めない |
  | 4 | 入力の誤り（入力のファイルの形式、条件の値の誤り、親のツールパスの成果物の形式の誤り）。やり直しても同じ結果になる |
  | 5 | 計算の失敗（経路が得られない・収束しない・切削シミュレーションの失敗など） |
  | 6 | 成果物・ログ・進み具合を書けない |
  | 7 | ツールパスの点の数がメモリの上限を超えるため止めた（#1234） |

  4・5・7 は、ログに失敗の分類（`code=`）と理由を書く。計算の前に、出力のフォルダの前の実行の成果物を消す（失敗した実行の成果物に見えないように）
- ツールパス生成は、パスの点の数を走査ラインごとに数え、メモリの上限（既定は 8 GB）を点 1 つあたりのメモリの見積もり（250 バイト。生成の間のパスの点と線分、成果物のバイト列を作る間の線分とバイト列のうち多い側）で割った数を超えたら止める（メモリを使い切る前に止まり、ほかのアプリやドライバーを巻き込まない。#1234）

- ランナーは入力のファイルの読み込みと計算を `cam_sim` の関数（`read_cam_solver_input_v1`・`read_cutting_simulation_input_v1`・`run_cam_solver`・`run_cutting_simulation`）に任せる。同じプロセスの中で実行する今のジョブのアダプタ（`CamJobExecutorAdapter`）も、同じ計算の関数を使う
- Docker の実行のイメージ（`Dockerfile.batch`）は、今は仮のスクリプト（`scripts/batch_runner_stub.sh`）のまま。ランナーの実行ファイルに替えるのは、Docker・K8s のバッチで実行するときに行う

### 3.2 ジョブマネージャーの実行ファイル（#1077）

ジョブマネージャーのサービス（`JobManagerService`）は `job_manager` のクレートに置き、実行ファイル `redring-job-manager` は View の層の `job_manager_app` のクレートに置く（画面。`CAM_OPERATION_UI_DESIGN.md` 3.7）。

```text
redring-job-manager [--store <ジョブの保存先>] [--background]
```

- サービスの仕事は、画面とは別のスレッドで行う。`--background` のときはウィンドウを出さない（CAD/CAM のアプリから起動したとき・OS の起動のとき。Windows ではタスクトレイだけを出す）。指定しなければ、ジョブの一覧のウィンドウを出す。タスクトレイ・終了・2 つ目の起動は `CAM_OPERATION_UI_DESIGN.md` 3.7

- 保存先を指定しなければ、既定の保存先（4.1）を使う。指定する保存先は絶対のパスに限る（起動したフォルダで保存先が変わらないように）。起動のときに `manager.lock` を排他に開けなければ、終了の番号 1 で終わる（4.3）
- ランナーは、ジョブマネージャーの実行ファイルと同じフォルダの `redring-batch-runner` だけを、シェルを通さずに起動する（4.6）。引数のパスは、保存先のジョブのフォルダの決まった名前だけとする
- 0.5 秒ごとに、受付のフォルダの取り込み、終わったランナーの記録、実行できないジョブの失敗（5.5）、次のジョブの起動を行う。OS の変化の通知は、間隔を短くする必要が出たときに足す
- 同時に実行するジョブは 1 つ（9 章の残り）
- ランナーの終わり方で状態を決める。終了の番号 0 で成果物があれば正常に終わったとし、成果物・ログの参照（`result://<cam|sim>/<番号>/ok`・`log://<cam|sim>/<番号>/ok`）を記録する。それ以外は失敗とし、終了の番号の意味とログの最後の行を理由に記録する（ランナーが決めた終了の番号でない・番号のない終わり方のときは、標準エラー出力を先に見る。panic なら panic の文、そうでなければ最後の行）。ツールパスを読んでいる途中の読み込みの誤りは、入力を読めない（終了の番号 3）とする（途中で切れたファイルは、入力の誤り）
- 起動のときに、前に実行中だったジョブは中断にする（3.3。ランナーは別のプロセスのため、止まったジョブマネージャーからは引き継げない）。待ちのジョブはそのまま引き継ぐ
- ジョブの操作は、ジョブマネージャーの画面から頼む（#1079。`CAM_OPERATION_UI_DESIGN.md` 3.7）
  - 取り消し（`JobManagerService::cancel`）は、実行中ならランナーのプロセスを止め、取り消しの状態にする
  - 再計算（`retry`。画面の文言は #1232 で「やり直し」から変えた）は、失敗・取り消し・中断のジョブを待ちに戻し、最初から計算する。依存関係（前・後のどちら向きも）でつながる、失敗・取り消し・中断のジョブもあわせて戻す（前のジョブが終わったままでは実行できず、後のジョブは前のジョブの失敗で失敗になっているため）。戻すジョブの前の成果物・ログ・進み具合・途中の結果を先にすべて消し（消せなければ記録を変えない）、試行の回数は数え続ける
  - 計算（`resume`）は、中断のジョブを、途中の結果を残して待ちに戻す（3.3）
  - 削除（`delete`）は、選んだジョブ（複数を選べる）を、その成果物を使う後のジョブ（依存関係をたどったすべて）とあわせて消す（`delete_plan`。後のジョブだけが残っても、計算も取り込みもできないため）。選んだジョブか後のジョブのどれかが待ち・実行中なら、どれも消さずに残す（中断のジョブを待つ待ちのジョブは除く。3.3）。後のジョブだけを選んだときは、前のジョブを残す。後のジョブから消す（途中で消せなくなっても、成果物を使う後のジョブだけが残らないように）。ジョブの番号は使い直さない（4.5.1）
  - 優先順位の変更（`change_priority`）は、待ちのジョブと、それを待つ待ちの後のジョブの記録の優先順位を同じだけ変える（待っているジョブの優先順位は前のジョブに伝わるため、前のジョブだけを下げても順が変わらない。5.5）
- 出来事は、保存先の `manager.log`（英語。起動のたびに書き直す）に書く。読めない記録・見送った投入は、最初に分かったときだけ書く。保存先を読み書きできない誤りは書いて、できるところまで続け、次の回にやり直す
- ジョブの記録を書けないときは、起動したランナーを止めて待ちに戻し（二重に起動しない）、終わったランナー・取り消したランナーは次の回に記録し直す
- 進み具合（`progress.json`）は、ジョブマネージャーの画面（#1079）と CAD/CAM のアプリ（#1078）が読む

### 3.3 中断と続きからの計算（#1235）

計算中にジョブマネージャーが止まったジョブは、失敗ではなく中断とし、利用者が選べば途中から計算を続ける。Windows Update などで OS が再起動して、時間のかかるツールパス生成（10 分以上のこともある）が途中で止まることが多いと見込まれるためである。

#### 中断の状態

- ジョブの記録の状態に、中断（`interrupted`）を足す。中断になるのは、次のジョブとする
  - トレイの「終了」で止めた、計算中のジョブ（終了の確かめの文言も、中断になることに変える）
  - 起動のときに、前に実行中だったジョブ（ジョブマネージャーの異常終了・OS の再起動で止まったもの。OS の終わりの通知は受けないため、OS の再起動もこの形になる）
- 取り消し（ジョブマネージャーの画面の取り消し・工程リストの計算停止）は、今までどおり取り消しとする
- 中断は、自動では続けない。利用者が計算するか（続ける・最初から計算し直す・消す）を選ぶ
- 中断のジョブを待つ後のジョブ（切削シミュレーション）は、失敗にせず、計算待ちのまま待つ（前のジョブを計算で続けたら、そのまま後のジョブも進むように）。計算の順を決めるときは、依存先が中断のジョブは実行しないが、失敗にもしない。中断のジョブは、ほかのジョブの優先順位を上げない
- 削除・まとめて削除（古いジョブは除く。7 章）では、中断のジョブと、それを待つ待ちの後のジョブ（中断のジョブを続けるまで実行されない）を、終わったジョブと同じに扱い、あわせて消せる（ランナーが動いていないため。後のジョブが待ちのまま残って、中断のジョブと途中の結果を消せなくならないように）
- 起動のときに中断にしたジョブがあれば、トレイの吹き出しで示す（中断は自動では続けず、利用者が選ぶまで計算が進まないため）。トレイの「終了」で中断にしたときは示さない（利用者が終えたため）
- 前の版の記録の失敗（誤りの種類が `ManagerStopped`・`ManagerQuit`）は、失敗のままとする（途中の結果を持たないため、中断にしても最初から計算することになる）
- 記録の形式の版: 中断の記録は版 4 で書き、ほかの記録は今までどおり版 3 で書く（表せる最も古い版で書く。9 章）。前の版のジョブマネージャーは、中断の記録を読めない記録として扱う
- 口（`JOB_IPC_DESIGN.md`）の状態にも中断を足し、口の版を 2 に上げる（前の版のアプリは知らない状態を読めず、ジョブの一覧をまるごと読めなくなるため。版が違えば、アプリは計算などの操作の失敗の理由に、ジョブマネージャーを起動し直すように出す。状態の読み取りは、読めないと出す）

#### 操作

- ジョブマネージャーの画面
  - 計算（`resume`）: 中断のジョブだけを選んでいるときに押せる。選んだ中断のジョブと、それが待つ（依存関係で前の）中断のジョブを、途中の結果を残して待ちに戻す。前の実行のログ・進み具合は消す。試行の回数は数え続ける
  - 再計算: 中断のジョブも押せる。途中の結果も消して、最初から計算する（3.2）
  - 取り消し: 中断のジョブも取り消せる（取り消しの状態にする）。取り消すと、計算中・中断のどちらでも途中の結果を消す（取り消したジョブは続けられず、再計算は最初から計算するため）
- CAD/CAM のアプリ（`CAM_OPERATION_UI_DESIGN.md` 3.5）
  - 工程の状態に中断を足す。切削シミュレーションが計算待ちで、ツールパス生成が中断なら中断とする（失敗・取り消しと同じ扱い）
  - 計算: 今の条件のジョブに中断のものがあれば、新しく投入せず、口の `resume` でそのジョブの計算を頼む（ジョブマネージャーが動いていなければ起動する）
  - 再計算: 今のまま新しく投入し、前のジョブ（計算待ち・計算中・中断）を取り消すように頼む
  - 計算停止: 今のまま計算待ち・計算中のときだけ押せる（中断は止まっているため）
  - 前の改訂のジョブの取り消し（9 章、#1296）には、中断のジョブも含める（前の改訂のジョブを、後から続けられる形で残さないため）

#### ランナーを残さない

- 今は、ジョブマネージャーが異常終了しても、ランナーは止まらずに終わりまで動く。中断のジョブを続けると、残ったランナーと新しいランナーが、同じ途中の結果のファイルに書くおそれがある
- Windows では、ジョブマネージャーは、ランナーをジョブオブジェクト（`JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`）に入れて起動する。ジョブマネージャーのプロセスが終わると、OS がランナーを止める
- ランナーの起動（`ProcessLauncher`）を、OS に依存するコードを集めるクレートへ移してから入れる（業務のクレートに OS への依存を入れないため。#1310）
- ほかの OS での止め方は、9 章の残りとする。決めるまでは、今の再計算と同じく、残ったランナーと新しいランナーが重なるおそれが残る

#### ツールパス生成の途中の結果

- 途中の結果は、計算の区切りごとの記録とし、役割を次の 2 つに分ける。ランナーが計算の中の作りを知らずに済み、計算の中身が変わったり加工の種類が増えたりしても、途中の結果の仕組みを変えずに済むようにするため
  - 計算（加工の種類ごとのアルゴリズム）: 区切りを終えるたびに、その区切りで増えた成果と、続けるための状態を出す。区切りと状態に何を入れるかは、計算だけが決める。続けるときは、それまでの記録の成果を順に受け取り、最後の記録の状態から計算を再開する
  - ランナー: 成果と状態を、中身を見ないバイト列として書き足し、検査の値で確かめて読み戻す
- 区切りを作るのは、今はスキャン加工だけとする。スキャン加工は、走査線ごとの計算が入力だけから決まる（前の線の結果を使わない）ため、走査線を区切りにする。続けるための状態は、次の走査線の番号・往復の向きを決める番号（加工領域にかかり、幅のある線だけを数えたもの）・パスの番号・点の数の合計（メモリの上限。3.1）とし、成果はその線のパスとする。区切りを作れない加工の種類は、続きから計算せず、最初から計算する
- 途中の結果は、ジョブのフォルダの `resume/toolpath.resume` に、ランナーが書く。ジョブマネージャーは、ツールパス生成のランナーに `--resume` でこのファイルを渡す
  - 名前を `*.tmp` にしない（起動のときの片付けで消されないように）。`output/` にも置かない（ランナーが計算の前に成果物を消すため）
- ファイルの形
  - 頭: 種別・形式の版・ランナーの実行ファイルの検査の値・入力のファイルの検査の値・加工の種類
  - 続けて、区切りごとの記録（記録の通し番号・状態のバイト列・成果のバイト列・記録の検査の値）を、区切りの順に書き足す。計算が区切りを出したときだけ書く（加工領域にかからない走査線など、成果のない所は記録を書かなくてよい。次の走査線の番号は状態が持つため）
  - 検査の値は、書きかけ・偶然の壊れを見分けるためのもの（書き換えへの備えではない）。新しい依存クレートは足さずに作る
- 書き方: 区切りを終えるたびに記録を書き足す。ドライブへの書き込みを確かめる（`sync`）のは、数秒に 1 回とする（区切りごとに確かめると、短い区切りの多い計算で遅くなるため。OS の再起動で最後の数秒の記録が失われても、その区切りから計算し直すだけで済む）。全体を書き直さない（点の数が多いとき、書き直しの量が大きくなるため）
- 使えるかの確かめ（ランナーが計算の前に行う）
  - 頭の種別・形式の版、ランナーの実行ファイルの検査の値（版の番号は、計算の中身が変わっても上がらないことがあるため、実行ファイルそのもので見る）、入力のファイルの検査の値、加工の種類が、今の計算と同じであること。違えば、ファイルを捨てて最初から計算する
  - 記録は、通し番号が 0 から続き、検査の値が合うところまでを使う。壊れた記録と、その後ろは捨て（ファイルをそこで切り詰め）、最後の正しい記録の状態から計算する
  - 読み込みは信用できない入力として扱う（4.6）。ランナーは、記録の長さを上限で確かめてから読む。状態と成果の中身は、それを読む計算の側が確かめる（点の数は、メモリの上限（3.1）で確かめてから確保する）
- 途中の結果がない・使えないときは、最初から計算し、使えなかった理由をランナーのログに書く（画面には出さない）
- 続きから計算した成果物は、最初から計算した成果物と同じになる（試験で確かめる）。工具・形状の準備（分割・逆オフセットの形）は、続けるときも作り直す
- 途中の結果を消すとき: ランナーが成果物を書き終えた後、取り消し・再計算・削除のとき。成果物の大きさの合計（7 章）にも数える

#### 切削シミュレーション

- 切削シミュレーションも、止まれば中断にする。ただし、途中の結果を持たないため、計算すると最初から計算する
- 切削シミュレーションは、走査線のような独立した単位ではなく、素材の状態から、工具が通る形を順に引いていく。続きから計算するには、引いている途中の素材の状態（数十 MB）と、それまでの変化（再生のキーフレーム）を書き残す仕組みが新しく要る。サンプルデータでも計算は数十秒で、時間がかかるのはツールパス生成のため、続きから計算することは別の Issue とする（区切りと状態を計算が決める、上と同じ枠に載せる）

#### 段階

| PR | 内容 |
|---|---|
| 1 | この設計の文書 |
| 2 | 中断の状態と操作（記録・口の版、ジョブマネージャーの画面の計算、アプリの計算・再計算、マニュアル）。この段階では、計算すると最初から計算する |
| 3 | ランナーを残さない（#1310 で、ランナーの起動を OS に依存するコードを集めるクレートへ移した後） |
| 4 | ツールパス生成の途中の結果と、続きからの計算 |

## 4. 受け渡し（共有フォルダ）

CAD/CAM のアプリとジョブマネージャーは、共有フォルダ（ジョブの保存先）を読み書きして受け渡す。

### 4.1 フォルダの構成

```text
<ジョブの保存先>/
  manager.lock              ジョブマネージャーが OS のファイルロックで排他に開く（1 つだけの起動）
  last_job_id               使ったジョブの番号の最大（ジョブを消したときに書く）
  inbox/
    <投入の ID>/            CAD/CAM のアプリが置く投入（要求と入力）
    <投入の ID>.rejected/   取り込めなかった投入（reason.txt に理由。英語）
  jobs/
    <ジョブの番号>/
      job.json              ジョブの記録（ジョブマネージャーだけが書く）
      input/                入力（投入から移す）
      output/               成果物（ランナーが書く）
      logs/                 ログ（ランナーが書く）
      progress.json         進み具合（ランナーが書く）
      resume/               途中の結果（ツールパス生成のランナーが書く。3.3）
```

- ジョブの保存先は、ジョブマネージャーの設定（根のフォルダ）とする。既定は、利用者ごとのローカルのアプリのデータのフォルダの下（Windows では `%LOCALAPPDATA%\RedRing\jobs`）。利用者のフォルダに置くことで、フォルダの権限により、ほかの利用者から読み書きされない
  - ジョブマネージャーは、起動の引数 `--store`、なければ設定のファイル（`job_manager.json`）の項目 `store`（絶対のパス）、それもなければ既定の保存先を開く（#1178）
  - 設定の保存先を開いたときは（試しに `--store` で別の保存先を指定して起動したときは開かない）、ジョブマネージャーに問い合わせる口を開く（`JOB_IPC_DESIGN.md`。#1183）。CAD/CAM のアプリは、保存先の場所を知らず、口で問い合わせる。アプリがジョブマネージャーを起動するときは、保存先を渡さない（ジョブマネージャーは設定の保存先を開く）。設定の保存先は、ジョブマネージャーの画面で替える。項目 `store` が絶対のパスの文字列でなければ、起動の誤りにする（黙って既定の保存先にしない）。ジョブマネージャーが保存先を替えても、アプリを起動し直さずに追う
  - 画面で替えるときは、待ち・計算中のジョブ（中断のジョブを待つものを除く。利用者が操作するまで計算しないため。3.3）、取り込みを待つ投入がないこと（今の保存先に残り、計算されなくなるため）、選んだフォルダがこの PC のフォルダ（UNC のパス・ネットワークのドライブでない）で、今の保存先と同じでも入れ子でもないこと、保存先でないのに保存先の中のもの（受付・ジョブのフォルダ、ロックのファイル）と同じ名前のもの（ほかの保存先など）を含まないことを確かめる。空でもジョブの保存先でもないフォルダは、確かめの画面で示す。選んだフォルダを保存先として開けたら設定に書き（書けなければ、開いたときに作った空のフォルダを消す）、Windows の起動のときのコマンドが保存先を指定していれば指定しないコマンドに書き直し、新しいジョブマネージャーのプロセスを起動して、今のプロセスを終える（保存先が違うため、ロックとトレイの見えないウィンドウは重ならない）。起動し直せなかったときは、今の保存先のまま動き続ける（次の起動は新しい保存先になる）。前の保存先のファイルは消さない
  - 替える直前に CAD/CAM のアプリが前の保存先に書いている途中の投入は、前の保存先に残る（前の保存先に戻せば取り込む）
  - ほかの利用者が書き込めるフォルダかは確かめない（利用者のマニュアルで、書き込めないフォルダを選ぶように書く）
  - Windows の起動のときに起動するコマンドは、設定の保存先と違う保存先を指定して起動したときだけ `--store` を付ける（後で設定の保存先を替えても、替えた保存先で起動するように）
  - アプリとジョブマネージャーの間を、ファイルの場所に頼らない問い合わせの口にすることは、別の PC のジョブマネージャーを扱うときに行う
- 最初は、同じ PC のローカルのフォルダとする。ネットワークの共有フォルダ（SMB）は、名前の変更と変化の通知の信頼性が下がるため、扱わない
- 保存先の読み書きは `job_runtime::store`（`JobStore`）に置く。ジョブマネージャーと、#1078 で投入・状態の読み取りを替える CAD/CAM のアプリが、同じコードを使う

### 4.2 書きかけを読まない決まり

- 1 つのファイル・フォルダを書くのは、1 つのプロセスだけとする（投入は CAD/CAM のアプリ、ジョブの記録はジョブマネージャー、成果物・ログ・進み具合はランナー）。同時に書くための排他は要らない
- ファイルは、一時の名前（`*.tmp`）で書き終えてから、正しい名前に変える。同じドライブの中の名前の変更は一度に切り替わるため、読む側は `*.tmp` を無視するだけで、書きかけを読まない。書く側が途中で落ちても、残るのは `*.tmp` だけで、ジョブマネージャーが起動のときに片付ける
- 投入は、フォルダごと一時の名前（`inbox/<投入の ID>.tmp/`）で作り、要求と入力をすべて書いてから、フォルダの名前を変える
- 書きかけの判断にロックファイルは使わない（書く側が落ちると古いロックが残り、その片付けが要るため）

### 4.3 1 つだけの起動と、起動の確認

- ジョブマネージャーは、起動のときに `manager.lock` を OS のファイルロックで排他に開き、終わるまで開いたままにする。開けなければ、ほかのジョブマネージャーが動いているので、起動をやめる
- OS のファイルロックは、プロセスが落ちると OS が外すため、古いロックの問題は起きない（ファイルがあるかどうかでは判断しない）
- CAD/CAM のアプリは、投入の前に `manager.lock` を排他に開けるかを試す。開ければ、ジョブマネージャーが動いていないので、すぐ閉じてジョブマネージャーを起動する。投入は、ジョブマネージャーが動いていなくても受付のフォルダに置けるため、起動を待たずに置いてよい（ジョブマネージャーは起動のときに受付のフォルダを読む）

### 4.4 投入の流れ

1. CAD/CAM のアプリは、投入の ID（UUID）を作り、`inbox/<投入の ID>.tmp/` に、要求（`request.json`）と入力（ツールパス生成の入力・切削シミュレーションの入力）を書く。要求は、ジョブの種類・親子（CAM の計算とその子の切削シミュレーション）・投入元（工程の ID と改訂の番号・改訂の鍵）を持つ
2. 書き終えたら、フォルダの名前を `inbox/<投入の ID>/` に変える
3. ジョブマネージャーは、受付のフォルダの変化（OS の通知。取りこぼしに備えて一定の間隔でも読む）で投入を見つけ、ジョブの番号を振り、入力を `jobs/<ジョブの番号>/input/` へ写し、ジョブの記録を書き、投入のフォルダを消す
4. ジョブの記録は、投入の ID を持つ。CAD/CAM のアプリは、投入の ID または投入元（工程の ID と改訂の鍵）で、自分の投入したジョブを引く

- 投入の ID は、ASCII の英数字・`-`・`_` の 64 文字以内（`.` を含まない。`.tmp`・`.rejected` の名前と分けるため）
- 要求（`request.json`）は、形式の版と、ジョブの列（種類 `cam`・`sim`、入力のファイルの名前、依存先、優先順位、グループ、投入元）を持つ。依存先は、同じ投入の前に並ぶジョブの位置（`submitted`）か、すでにあるジョブの番号（`existing`）で指す（後ろのジョブを指せないため、依存関係は循環しない）。切削シミュレーションは、ツールパス生成のジョブにちょうど 1 つ依存する（そのジョブの成果物をランナーの `--toolpath` に渡す）か、依存せずに CL のファイル（`toolpath_file`。投入のフォルダの中のファイル）を持つ（どちらか一方。空間モデルに取り込んだ CL から切削シミュレーションだけを計算し直すとき。CL はジョブの入力のフォルダの `input/toolpath.bin` に写し、ランナーの `--toolpath` に渡す。#1080）
- 検証できない投入は、`<投入の ID>.rejected` に名前を変えて理由を置き、取り込まない。投入した側は、ジョブが現れないことと理由のファイルで分かる
- 取り込みは、ジョブを `jobs/<ジョブの番号>.tmp/` に作ってから名前を変え、すべて作ってから投入のフォルダを消す。入力は移さずに写す（途中で止まっても、投入の入力が残り、取り込み直せるため）
  - すべてのジョブを作った後、投入のフォルダを消す前に止まった場合は、同じ投入の ID のジョブがあることで、二度目を取り込まない（投入の ID は、投入する側が重ならない値（UUID）にする）
  - 一部のジョブだけを作って止まった場合は、作ったジョブ（まだ実行していない）を消して取り込み直す
  - 投入のファイルを読み書きできない（ほかのプロセスが開いている等）投入は、その回は見送り、ほかの投入を続ける
  - 記録を読めないジョブ（壊れた `job.json`）は、投入の ID が分からないため、二度目の取り込みを防げず、依存先にもできない。壊れた記録は一覧で知らせる（ジョブマネージャーの画面で扱う）
- 起動のときの片付けは、ジョブのフォルダの `*.tmp` を消す。受付のフォルダの `*.tmp` は、CAD/CAM のアプリが書いている途中のことがあるため、更新から 1 時間を過ぎたものだけを消す。`.rejected` の投入は、ジョブマネージャーの画面の片付けで消す（7 章）

- 最初は、CAD/CAM のアプリはジョブの状態を見るだけとし、取り消し・やり直しはジョブマネージャーの画面だけで行う。取り消しは、投入と違って実行中のジョブを止める操作で、頼んでから止まるまでの状態を扱う必要があるため、CAD/CAM のアプリから頼めるようにするのは、必要になった時点で足す
- 投入の要求は、ジョブの依存関係（5.5）を持つ。依存先は、同じ投入の中のジョブか、すでにあるジョブの番号で指す

### 4.5 状態の受け取り

- CAD/CAM のアプリは、`jobs/` の変化を OS の通知で受け取り（取りこぼしに備えて一定の間隔でも読む）、ジョブの記録と進み具合を読む。ジョブは数秒から数時間かかるため、数百ミリ秒の遅れは問題にしない
- CAD/CAM のアプリを開き直したときは、空間モデルに保存した加工工程（工程の ID と改訂の鍵）で、ジョブの記録を引き直す（#1068）
- 改訂の番号だけでは、複製したモデルファイル・保存せずに捨てた変更で、別々の中身に同じ番号が付くことがある。そのため、ジョブの投入元に改訂の鍵（改訂を上げるたびに作る UUID）を足し、鍵で引く（`SPACE_MODEL_FILE_DESIGN.md` 5.1。#1165）
  - 記録・要求の投入元の項目 `revision_key` は、書いていなくても読める（前の版の記録は持たない）。鍵のない記録は、今の改訂のジョブとみなさない
  - 鍵を足したときに、記録・要求の形式の版を 2 に上げた（CL のファイルを足したときに 3 に上げた）。前の版のジョブマネージャーは知らない項目を読み捨てるため、版を上げないと、トレイに残った古いジョブマネージャーが鍵を落として取り込み、アプリから今の改訂のジョブとして引けなくなる。版を上げると、古いジョブマネージャーは要求を拒み、アプリは計算の失敗として出す
  - 改訂の番号は、画面に出す・人が見分けるために残す

### 4.5.1 CAD/CAM のアプリの側の境界（#1078）

- Application の中に、ジョブの投入・状態の読み取り・成果物の取り込みの境界（`job_client` の `JobClient`）を置く。ユースケース（`CamSimulationWorkflow`）は境界だけを使い、後ろの実装を替えても（同じ PC の保存先のフォルダ・別の PC のジョブマネージャー）、ViewModel・画面は変わらない
- 今の実装は、ジョブマネージャーに問い合わせる口を通すもの（`PipeJobClient`。`JOB_IPC_DESIGN.md`。#1183）だけとする。計算は常にジョブマネージャーが行い、同じプロセスの中の実行には戻さない（試験だけは、同じプロセスの中で実行する実装を使う）
  - 投入: 入力（5.2）と要求を口で送り、ジョブマネージャーが受付のフォルダに書く（`JobStore::write_submission`）。投入の ID は、ジョブマネージャーが時刻・プロセスの番号・通し番号から作る（`new_submission_id`）
  - 口につなげなければ、アプリの実行ファイルと同じフォルダの `redring-job-manager` だけを、保存先を渡さずに起動し、口が開くのを待つ。起動したジョブマネージャーがすぐ終わった場合（ランナーがない・口を開かない前の版のジョブマネージャーが保存先を開いている等）は、待たずに理由つきの失敗にする。ないときは、投入を理由つきの失敗にし、状態は「ジョブがない」とする（CAD だけの操作はジョブを使わないため、ジョブマネージャーがなくても動く）
  - 状態: ジョブマネージャーが保存先の記録を読んで返す（読めない記録は読み飛ばす）。工程から引くときは、投入元（工程の ID と改訂の鍵）で引く
  - 取り込み: 入力と成果物を、口で大きさの上限つきで読む。ジョブマネージャーは、成果物のファイルを、記録の参照の文字列ではなく、ジョブの番号と種類から決まる名前で読む（書き換えた参照で、ほかのファイルを読ませない）
- アプリを開き直したときに、工程から前のジョブを引くことは、工程を空間モデルに保存してから（#1068。`SPACE_MODEL_FILE_DESIGN.md` 9 章）とする。今の工程の ID は起動のたびに作る
- 画面: 加工条件のウィンドウを開いている間、工程の今の改訂で最後に投入した計算の状態（待ち・計算中・終わった・失敗・取り消し・中断）を 1 秒ごとに読み直して出す（`CamSimulationWorkflow::latest_revision_job_states`）。切削シミュレーションが待ちで、ツールパス生成が計算中なら計算中、失敗・取り消し・中断ならその状態とする。ジョブマネージャーがまだ取り込んでいない投入（受付のフォルダ）は待ち、取り込めなかった投入は失敗とする。終わった状態は、ジョブマネージャーの画面でやり直す・消すと変わるため、5 秒ごとに読み直す。読むだけでは、ジョブマネージャーを起動しない（動いていない・見つからないときは状態不明。`JOB_IPC_DESIGN.md` 6 章）。保存先を読めないときは、読めないことを出す。「投入したらすぐ実行する」と `Shift+R`（実行）はなくした
- 配布物の zip に、アプリ・ジョブマネージャー・ランナーを同じフォルダに入れる（`dev/RELEASE_DISTRIBUTION_OPERATION.md`）

### 4.6 セキュリティ基準

ジョブの保存先は、同じ利用者のほかのプロセスからも読み書きできる。受付のフォルダの投入と、ジョブの保存先のファイルは、信用できない入力として扱う。

- 参照（`input_ref`・`result_ref`・`log_ref`）からファイルの名前を作るときは、ジョブの番号と接尾辞から決めた名前だけを使い、`..`・絶対パス・パスの区切りを含む値を拒む。作った名前が `jobs/<ジョブの番号>/` の下に収まることを確かめる（パスの書き換えで、保存先の外のファイルを読み書きさせない）
- 受付のフォルダの投入の要求（JSON）と入力のファイルは、ジョブマネージャーが取り込む前に検証する（形式の版・ジョブの種類・依存先の番号・大きさの上限）。ジョブの記録・進み具合のファイルを読む側（CAD/CAM のアプリ・ジョブマネージャー）も、壊れたファイルで落ちない
- 入力・成果物のバイナリの読み込みは、個数・長さの上限を確かめてからメモリを確保する（#1083）
- ランナーは、シェルを通さずに、実行ファイルのパスと引数を直接渡して起動する。引数に、投入の要求の文字列をそのまま入れない（ジョブの種類は決まった値の一覧から選び、パスはジョブマネージャーが作ったものだけを使う）
- 起動するランナー・ジョブマネージャーの実行ファイルは、インストールしたフォルダの決まった場所のものだけとし、作業のフォルダや PATH から探さない
- ジョブの保存先は、利用者だけが読み書きできるフォルダに置く（4.1）。ネットワークの共有フォルダは扱わない
- 同じ利用者のほかのプロセスが、投入を置けることを前提にする。投入元を名乗る値（工程の ID 等）は、ジョブの記録に残すが、権限の判断には使わない
- ログ・ジョブの記録に、秘密の値（認証の鍵等）を書かない
- localhost の通信の窓口を足すときの認証（127.0.0.1 だけで待つこと・認証の鍵・送り元の確かめ）は、窓口を足すときに決める（9 章）

## 5. ジョブの記録・入力・成果物

### 5.1 ジョブの記録

- ジョブごとに `jobs/<ジョブの番号>/job.json` に置く（組み込みのデータベースは使わない）。項目は、今のジョブの記録（`JobRecord`）と同じく、種類・入力の参照・投入元（工程の ID・改訂の番号・改訂の鍵。CL から投入した場合は CL の編集の番号）・依存するジョブ（親を含む。5.5）・優先順位・グループ・状態・試行の回数・作成と更新の時刻・成果物の履歴（参照と有効性）・直近の誤り、に投入の ID を足す
  - 今の項目（`StoredJob`）: 形式の版・ジョブの番号・投入の ID・種類・依存するジョブの番号・優先順位・グループ・投入元・状態（`queued`・`running`・`succeeded`・`failed`・`canceled`・`interrupted`。中断は 3.3）・試行の回数・作成と更新の時刻（UNIX 時刻のミリ秒）・成果物とログの参照・直近の誤り（英語の文）と、その種類（`error`。依存するジョブの失敗・ランナーの終了の番号の意味・計算中のジョブマネージャーの停止など。ジョブマネージャーの画面は、種類から画面の言語の文言を作る。種類のない前の版の記録は、英語の文を出す。#1162）。入力はジョブのフォルダの決まった名前（`input/input.bin`。CL のファイルを持つ切削シミュレーションは `input/toolpath.bin` も）のため、参照を持たない。やり直せるのは失敗・取り消し・中断のジョブ（成果物を持たない）だけのため、成果物の履歴は持たない
- 形式は、人が読めて、ほかの言語・道具からも読めるテキスト（JSON）とする。投入の要求も同じ形式とする（後で localhost の通信の窓口を足すときに、要求と応答の形としてそのまま使えるようにする）
- ジョブの番号は、起動のときに `jobs/` の中の最も大きい番号から続けて振る（ジョブマネージャーを再起動しても重ならない）。ジョブを消すときは、使った番号の最大を `last_job_id` に書き、それより大きい番号から振る（消したジョブを待つジョブ・CAD/CAM のアプリが持つ番号が、別のジョブを指さないように）。`last_job_id` を読めないときは、取り込みを見送る
- 一覧を出すときは、起動のときにすべてのジョブの記録を読み、その後は変化したジョブの記録だけを読み直す

### 5.2 入力

- ツールパス生成の入力（`CamSolverInput`。製品形状を含む）と切削シミュレーションの入力（`CuttingSimulationInput`）を、成果物と同じ共通のヘッダのバイナリ形式（`ARTIFACT_BINARY_IO_CONTRACT_DESIGN.md`）のファイルにする。形式の版を共通のヘッダで持ち、読み込みで確かめる
  - 種別は `RRCI`（ツールパス生成の入力）・`RRSI`（切削シミュレーションの入力）。中身の並びは `cam_sim` の `job_input_file` のモジュールの説明を正本とする。製品形状は、三角形メッシュと NURBS 曲面の集まりの両方を持てる
  - 読み込みは信用できない入力として扱い、個数から確保する前に残りのバイトの数で足りることを確かめる。条件の値の検証は、計算の入口（ツールパス生成の入力の検証・切削シミュレーションの Preflight）で行う
- 入力は、ジョブごとに持つ（同じ製品形状を複数のジョブで共有しない。ジョブを消したときに、ほかのジョブに影響しないため）

### 5.3 参照と置き場所の対応

- 入力・成果物・ログの参照（`input_ref`・`result_ref`・`log_ref`）は、今の参照の決まり（`ARCHITECTURE.md` の「参照識別子・パス文字列運用ルール」。スキーム・ドメイン・ジョブの番号・接尾辞）のまま、ジョブの番号と接尾辞から `jobs/<ジョブの番号>/` の下のファイルの名前が一通りに決まる規則にする
- 参照からファイルの名前への変換は、参照のファクトリ・パーサー（`job_runtime::reference`）の側に置き、呼び出し元で組み立てない
  - 変換は `JobStore::file_for_ref` とし、参照の読み取りは `RefParser` を使う。`result://<cam|sim>/<ジョブの番号>/...` は成果物（`output/toolpath.bin`・`output/cutting_simulation.bin`）、`log://<cam|sim>/<ジョブの番号>/...` はログ（`logs/runner.log`）を指す。ファイルの名前は、ジョブの番号とドメインから決まる名前だけで作り、接尾辞はパスに使わない

### 5.4 素材のファイル

- 切削シミュレーションは加工手順に 1 つとし、工程ごとの区間を持つ（`CAM_PROCESS_ENTITY_DESIGN.md` 4.4）。実行は区間ごとのジョブとする
- 区間のジョブのランナーは、区間の終わりの素材を、成果物とは別の素材のファイル（`RRST`。格子と各線の材料の区間）として `output/` に書く（`CAM_PROCESS_ENTITY_DESIGN.md` 6.3。格子は手順で 1 つで、すべての区間で同じ）
- 区間の終わりの素材のファイルは、次の区間の始まりの素材と、素材を使う工程の CAM の計算の入力になる（ジョブをまたぐ入力。入力の参照で前の区間のジョブの素材を指す。`stock_ref`）
- 入力の参照がほかのジョブの成果物を指す場合は、そのジョブへの依存関係（5.5）を必ず持つ
- 区間のジョブは、その工程の CAM の計算と前の区間のジョブの 2 つに依存し、ジョブマネージャーは依存するジョブの種類で入力（CL・始まりの素材）を決める。要求に素材の依存を足すときに、記録・要求の形式の版を上げる。区間の結果は、投入元の区間の前提の鍵（その工程と前の工程の改訂の鍵の列・格子）で、今の結果かを見分ける（`CAM_PROCESS_ENTITY_DESIGN.md` 6.3）

### 5.5 依存関係と計算の順

- ジョブは、依存するジョブ（複数）を持つ。今の親（1 つ）だけの関係を、複数の前のジョブを待てる関係に広げる。依存するジョブがすべて正常に終わったジョブだけを実行する。依存するジョブが失敗・取り消しで終わったら、実行せずに理由つきで失敗にする。依存するジョブが中断なら、実行せず、失敗にもせずに待つ（3.3）
- 工程 1・工程 2 の手順の依存関係（矢印は、済んでから始める）

  ```text
  工程 2 が素材を使わない場合:
    工程1 CAM ──→ 区間1（シミュ） ──(素材)──→ 区間2（シミュ）
    工程2 CAM ────────────────────────────────↗
  工程 2 が素材を使う場合:
    工程1 CAM ──→ 区間1（シミュ） ──(素材)──→ 工程2 CAM ──→ 区間2（シミュ）
  ```

  - 素材を使わない工程の CAM の計算は、ほかの工程と並べて計算できる
  - 素材を使う工程は、前の区間から続く一続きの塊になり、塊の中の順は変えられない
  - 切削シミュレーションの区間は、素材を受け渡すため、加工の順の一列になる
  - 切削シミュレーションをしない工程（`CAM_PROCESS_ENTITY_DESIGN.md` 4.4）は、区間のジョブを作らず、前の区間の素材をそのまま次へ渡す
- 加工の順（手順の中の工程の並び）と計算の順は分ける。計算の順を変えても、加工の順（NC の出力の順・素材の受け渡しの順）は変わらない
- 計算の優先順位
  1. 依存するジョブがすべて済んだジョブの中から、優先順位の高いものを先に実行する
  2. ジョブマネージャーの画面の「順番の上げ下げ」で、ジョブの優先順位を変える
  3. あるジョブの優先順位を上げたら、それが待っている、まだ済んでいない前のジョブも同じ高さまで上げる（上げたジョブが前のジョブを待ち続けないようにする）
  4. 優先順位を上げても、依存関係を飛び越えて先に実行しない
  - 3 は、記録の優先順位を書き換えずに、実行の順を決めるときに「実効の優先順位」（自分の優先順位と、自分を待っている終わっていないジョブの実効の優先順位の大きいほう）で行う。後から投入した優先順位の高いジョブが、すでにあるジョブを待つ場合も同じに扱える。同じ高さは番号の小さい（先に投入した）ジョブを先にする（`job_runtime::store` の `plan_schedule`）
  - 依存するジョブが失敗・取り消しで終わった・記録がない待ちのジョブと、それを待つジョブは、実行せずに理由つきで失敗にする。依存するジョブが中断の待ちのジョブは、失敗にせずに待つ（3.3）。実行できないジョブ・中断のジョブは、ほかのジョブの優先順位を上げない。記録を今は読めない依存先（ほかのプロセスが開いている等）は、読めるようになるまで待つ
  - 依存先は番号の小さいジョブに限る（投入の検証で前のジョブに限るため）。書き換えた記録で後の番号を指すジョブは、実行できないジョブにする（循環しない）
- 塊を作る操作は持たない。工程の「素材を使う」の入・切から依存関係が決まり、塊は自然にできる

### 5.6 進み具合

- ランナーは、`progress.json` に進み具合（割合・区間の番号など）を一定の間隔で書く（一時の名前から名前を変える）。ジョブマネージャーは、それを読んでジョブの一覧の進み具合のバーに出す（`CamJobEvent::ProgressUpdated` に当たる）
- ランナーの終わりの判断は、プロセスの終わり方（終了の番号）と成果物で行う。異常な終わり方は、失敗として理由（終了の番号・ログ）を記録する

## 6. 成果物と空間モデル

| 成果物 | 空間モデル（#1068）との関係 |
|---|---|
| CL（ツールパスの成果物） | 空間モデルの中へ、一方通行で取り込む（コピーする）。工程は CL を 1 つだけ持ち、取り込むたびに上書きする（工程と CL は 1 対 1 に結び付く）。ジョブの側の成果物と重複してよく、取り込んだ後は、空間モデルはジョブマネージャーに頼らない（NC の出力・ほかの人へ渡すときも、モデルファイルだけで足りる）。ジョブの側の成果物は消してよい |
| 切削シミュレーションの結果（差分のキーフレームの形式で、サンプルデータで数十〜百 MB 程度。`CUTTING_SIMULATION_STOCK_MODEL_DESIGN.md` 5.2。再生する間のメモリは数百 MB） | 取り込まない。ジョブマネージャーの置き場所に置いたまま、工程の ID と改訂の番号から引いて再生する。消した場合は、取り込んだ CL から切削シミュレーションだけを計算し直す |

- 取り込んだ CL は、取り込んだときの工程の改訂の番号と改訂の鍵を持つ。工程の改訂の鍵が変わったら、取り込んだ CL は今の条件の結果ではないことを画面で知らせる（加工条件のウィンドウの「空間モデルの CL」の行。#1080）
  - 切削シミュレーションの結果を取り込むときに、その CL も空間モデルに取り込む（保存していない変更になり、モデルファイルの区画 `CLDT` に保存する）
  - 空間モデルの CL が今の条件の結果のときは、切削シミュレーションだけを投入できる（加工条件のウィンドウの「切削シミュレーションだけ計算」。今の条件の計算が待ち・計算中・完了のときは押せない）。工程の今の改訂で正常に終わり、切削シミュレーションを置いていないツールパス生成のジョブが残っていれば、その下に置く（投入の要求の依存先 `existing`）。なければ空間モデルの CL を入力にする（`toolpath_file`）。ツールパス生成のジョブ 1 つに、切削シミュレーションは 1 つだけ置く。投入元は工程の ID と今の改訂の鍵のため、取り込みは今までどおり工程の今の改訂の結果として引く。CL を入力にした結果はツールパス生成の入力を持たないため、取り込んだ条件の走査線の条件とトレランスは、今の条件のものを出す
- CL の編集（後で足す）は、空間モデルの CL を書き換える
  - 工程の中身（条件）は変えないため、工程の改訂の番号は進めない。CL に「編集済み」と CL の編集の番号を持たせ、取り込んだ計算の結果から変わったことを表す
  - 編集済みの CL を、計算し直した結果で上書きする前には、編集が失われることを確かめる
  - ジョブの側の切削シミュレーションの結果は、編集する前の CL のものになるため、その工程の区間と後の区間（素材が変わるため）は再計算待ちになる。前の結果は消さずに残し、「前の CL の結果」として見比べに使える
  - 編集した CL からの切削シミュレーションは、空間モデルの CL を入力として投入する。ジョブの投入元に CL の編集の番号を足し、どの CL の結果かを見分ける
  - NC の出力は、空間モデルの CL（編集した後のもの）から出す
- 取り込んだ CL からの切削シミュレーションは、親の CAM の計算のジョブを持たない投入になる。今のジョブの関係の決まり（`BATCH_COMPUTE_PLATFORM_DESIGN.md` 14.8。親のない切削シミュレーションは許さない）に、取り込んだ CL を入力とする形を足す（実装の段階で決める）

## 7. 片付け

- ジョブの成果物は、利用者がジョブマネージャーの画面で消すまで残す（自動では消さない）
- ジョブマネージャーの画面に、成果物の大きさの合計を出し、まとめて消す操作を置く（#1157）。消すジョブは、1 つずつ消すときと同じ決まり（4.3 の削除。後のジョブもあわせて消し、待ち・実行中のものは残す）で決め、件数を出して確かめる
  - 前の改訂の結果（`superseded_jobs`）: 投入元の ID ごとに、最も後に正常に終わったジョブの改訂の鍵を今の改訂とみなし、それより前に投入した、ほかの鍵（鍵を持たない前の版の記録を含む）のジョブとする（後から投入して、まだ終わっていない・失敗したジョブでは決めない）。ジョブマネージャーはアプリの今の改訂を知らず、改訂の番号は複製したモデルファイル・保存せずに捨てた変更で重なるため、投入の順で決める（複製したモデルファイルを交互に使っているときは、使っている結果も前の改訂になり得るため、件数を出して確かめる）
  - 古いジョブ（`old_jobs`）: 画面で入れた日数より前に投入した、終わったジョブ（中断は含めない。続けるつもりの中断のジョブを、日数だけで消さないため。前の改訂の中断のジョブは、アプリが取り消すため、取り消しのジョブとして入る。3.3）。あわせて消える後のジョブも、すべてその日数より前に投入したものに限る（古いツールパス生成の下に、後から計算した切削シミュレーションを消さないように）
  - 取り込めなかった投入（受付のフォルダの `<投入の ID>.rejected`）。画面を開いたときにあったものだけを消す
  - 取り込み済みの CL の元（`imported_sources`）: アプリが CL を空間モデルに取り込んだと伝えた（ジョブのフォルダに取り込んだ印がある）、終わったツールパス生成のジョブ。あわせて、その結果を使う切削シミュレーションも消える。取り込んだ後に、同じツールパス生成の下に別の切削シミュレーションを置いていれば数えない（まだ取り込んでいない結果を消さないように）。取り込んだ印は、まとめて削除の画面を開いたときに 1 回読む。取り込んだのが別のモデルファイル・保存していない変更のときもあるため、件数を出して確かめる（`JOB_IPC_DESIGN.md` 5 章。#1191）
- ジョブを消すときは、`jobs/<ジョブの番号>/` を消す。成果物を使う後のジョブもあわせて消す（4.3）。CAD/CAM のアプリは、今の条件のジョブがなければ「ジョブがない（投入していない、または消した）」と出す。空間モデルに今の条件の CL があれば、切削シミュレーションだけを計算し直せる
- 切削シミュレーションの区間の結果を消すと、区間の終わりの素材のファイルもなくなる。入力を失うのは、素材を入力にするもの（後の区間と、素材を使う工程の CAM の計算）だけで、素材を使わない工程の CAM の計算（CL）は影響を受けない。消す前に後の工程への影響を知らせ、入力を失うものは再計算待ちとして扱う

## 9. 決めること（残り）

- 投入の要求とジョブの記録の JSON の版を上げるときの扱い（今は記録を版 3（中断の記録は版 4。3.3）で書き、版 1〜4 を読む。記録の失敗の理由の種類（`error`）は、前の版が読み捨てても英語の文が残るため、版を上げずに足した（知らない種類は、英語の文を出す）。要求は、表せる最も古い版で書く（CL のファイルを持たない要求は版 2、持つ要求は版 3。前の版のジョブマネージャーが残っていても、今までの投入は取り込める）。項目を足すときも版を上げ、前の版のジョブマネージャーに黙って取り込ませない。項目は 4.4・5.1）
- CAD/CAM のアプリから取り消しを頼めるようにする時期と、頼み方（受付のフォルダに取り消しの要求を置くか）
- 前の改訂の計算待ち・計算中のジョブは、消さずに取り消す（#1296）。CAD/CAM のアプリは、工程の改訂が進んだとき（計算の条件・手順の素材を変えて適用した、製品形状を取り込んだ）と、計算を投入した後に、加工手順のすべての工程について、投入元の工程の ID が同じで改訂の鍵が今と違う（鍵を持たない前の版の記録を含む）ジョブの取り消しを頼む。ジョブマネージャーが動いていなければ起動せず、次に計算を投入したとき（そのときは起動する）に取り消す。取り消したジョブは「やり直し」で戻せるため、ジョブを持つ単位の ID（下）を入れるまでは、同じ PC で複写したファイルのジョブも取り消しうることを許す
- 同じ工程を投入し直したときに、前のジョブをどうするか（#1218。保留）。今は前のジョブを残し、「まとめて削除」の前の改訂の結果で消す（7 章）。ジョブマネージャーを計算の管理だけにし、計算の条件と CL の正本を空間モデルに置く方針のもとで、次の案を検討した
  - 前のジョブを消して作り直す: ジョブマネージャーが投入を取り込むときに、同じ工程の前のジョブを取り消してから消す（新しい投入が依存先にするジョブは残す）。今ある取り消し・削除を使え、作る量は少ない
  - 前のジョブを使い回す: 前のジョブの成果物を消し、入力を入れ替えて計算待ちに戻す（ジョブの番号・依存先は変えない）。使い回したジョブを依存先にする後のジョブも計算待ちに戻せる（再計算の伝搬）。ツールパス生成の子の切削シミュレーションは使い回せるが、親を持つ・持たない（CL のファイルを入力にする）切削シミュレーションが入れ替わる場合は依存の形が変わるため、消して作り直すしかない
  - どちらも、ほかのファイルの写しのジョブに触れないよう、投入元に「ジョブを持つ単位の ID」を足すことが前提になる（下の ID の分け方）
  - 工程の ID のかぶりが問題になるのは、ジョブを消すとき（「まとめて削除」の前の改訂の結果、上の 2 案）だけである。ジョブを引く・取り込むときは、工程の ID と改訂の鍵が同じなら入力も同じため、2 つのファイルから同じ結果を使っても正しい
  - ID の階層: 空間モデルの ID は、空間モデル（モデルファイル）全体で 1 つ。その中に、面ごとの面の ID・エンティティの ID、加工手順の ID、加工工程の ID と今の改訂の鍵がある。ジョブは、加工工程の ID と改訂の鍵で引く
  - ID の分け方: 「同じモデル（物）であること」と「ジョブを持つ単位」を分ける
    | ID | 意味 | 名前を付けて保存・ほかの PC への写し | 同じ PC での複写 |
    |---|---|---|---|
    | 空間モデルの ID（今のもの） | 同じモデル（物）であること。協調設計で変更を比べる・まとめる、版を管理する、ほかの計算機のジョブマネージャーにつなぐときの手がかり | 変えない | 変えない |
    | ジョブを持つ単位の ID（上の 2 案を入れるときに足す） | この PC の、このファイルの写し。ジョブを消す範囲を決める | 変えない | 変える |
    - 名前を付けて保存・ほかの PC への写しで空間モデルの ID を保つのは、協調設計で、戻ってきたファイルが同じモデルだと分かるようにするため。ジョブマネージャーは PC ごと・利用者ごとのため、ほかの PC の写しとはジョブがかぶらない。ほかの PC で計算した結果は使えないが、条件を変えていない工程は、自分の PC で前に計算した結果を工程の ID と改訂の鍵で引ける
    - 同じ PC で、名前を付けて保存を別の案（バリエーション）を作るために使うと、2 つのファイルが同じ空間モデルの ID・工程の ID を持つ。ジョブを持つ単位の ID を入れるまでは、「まとめて削除」で消す前に件数を出して確かめる形で避ける
    - 工程の複写は、もとから新しい工程の ID を持つ。アセンブリで同じモデルファイルを何度も置く場合は複製ではなく、空間モデルの ID は同じまま、インスタンスの ID（道筋）で見分ける
  - 同じ PC での複写の見分け方の案: ファイルに、自分を最後に保存した場所を持たせる。開いた場所が記録した場所と違うとき、記録した場所に同じジョブを持つ単位の ID のファイルがまだあれば複写とみなしてジョブを持つ単位の ID を新しくし、なければ移動・名前の変更とみなして ID を変えずに場所を更新する。記録した場所のファイルの ID は、ID を持つ区画だけを読んで確かめる
    - 元のファイルを後から消した場合は移動とみなすが、同じ ID のファイルは 1 つだけになるため、かぶりは起きない
    - ほかの PC で開いた場合は、記録した場所がないため移動とみなす（ジョブを持つ単位の ID を変えない）。ジョブマネージャーは PC ごと・利用者ごとのため、ほかの PC のジョブとはかぶらない
    - 場所は、比べる前に書き方をそろえる（ネットワークのドライブの、ドライブ文字と UNC パスの違いなど）
    - 今の 1 つのモデルファイルでも使える。CAM のデータを別のファイルに分ける場合（#1211）は、CAM のファイルに参照する CAD のファイルの場所と ID を持たせ、CAD のファイルから CAM のファイルを開くときに、同じ見分け方で CAD の参照の更新と、CAM のファイルのジョブを持つ単位の ID の更新を行える
  - 後の工程への再計算の伝搬は、後の工程のジョブ（区間のジョブ。#1081）ができるまで対象がない。また、アプリの「手順の全体を投入」は今の結果がある工程を飛ばすため、伝搬は投入し直しでも行える。そのため、溜まるジョブは「まとめて削除」で消すこととし、#1081 の後に要るかを決め直す
  - 取り込んだ後にジョブの側の成果物を消すことは、切削シミュレーションの結果を CAM の側の正本にした後（#1211）に決める
- 実行中の成果物を途中から読むこと（切削シミュレーションの成果物の形式。#932）
- localhost の通信の窓口（自動加工の API・別の計算機のジョブマネージャー）を足す時期と、その認証の方法
- 同時に実行するジョブの数（CPU の数との関係）
- Windows 以外の OS で、ジョブマネージャーが異常終了したときにランナーを止める方法（3.3）
