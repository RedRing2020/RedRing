# CAM クレート責務設計と cam_algorithms 新設案

**作成日**: 2026年3月25日
**最終更新**: 2026年11月3日
**ステータス**: cam_algorithms 新設済み（#684）- 逆オフセット法による最小 solver 導線を実装（ボール/フラットエンドミル）
**関連Issue**: #413（親）、#426（分離）、#411、#412、#503、#504

---

## 📋 概要

現状の CAM 関連クレートは `cam_core`（データ/契約）・`cam_sim`（切削シミュレーション）・`cam_entity`（表示/属性統合）に分かれており、**経路生成・最適化・干渉回避などのアルゴリズム層の受け皿が明確でない**。

本設計では、`geo_algorithms` と対称的な責務分離を実現するため、`cam_algorithms` 新設を提案し、CAM クレート間の依存方向を確定する。

---

## 🎯 目的

1. **責務分離の明確化**: 各 CAM クレートが持つべき責務を一覧化
2. **依存方向の固定**: 許可/禁止される依存を定義し、将来実装の迷いを削減
3. **サーキュラー依存の回避**: `geo_*` 層との境界ルール確認
4. **段階導入の基盤**: 後続 Issue（アルゴリズム実装）の立案基盤

- ❌ `cam_entity`（表示層への依存は不可）

**現行実装**:

### 1.3 cam_sim（CAM特化ユースケース実行層）

**責務**:

- ToolPath の実行シミュレーション
- フレーム進行・時刻管理
- 切削体積計算（離散幾何ベース）
- シミュレーション結果のキャッシング

**位置づけ**:

- 物理配置は `model/` 配下だが、責務としては純粋データ層というより CAM ドメイン専用の実行・ユースケース層に近い
- `geo_algorithms` より上位で、`cam_core` が持つ中立データを消費してシミュレーションという業務処理を実行する
- そのため `cam_sim` は「Model内のCAM特化アプリケーション層」と捉えるのが実態に近い

**許可される依存**:

- ✅ `cam_core`（ToolPath 読み取り）
- 🔶 `cam_algorithms`（段階的・必要時のみ）
  - 理由: アルゴリズム関数の呼び出しが必要になる場合がある
  - ただし常時依存は避ける。インターフェッシングは最小化
- ✅ `geo_primitives`, `geo_algorithms`（幾何演算）

**禁止される依存**:

- ❌ `cam_entity`（表示層への直接依存は避ける）

**現行実装**:

- `model/cam_sim/src/`

**`cam_algorithms` を参照する具体例**:

- シミュレーション開始前の ToolPath 正規化
  - 例: `cam_algorithms::path_optimization` が近接セグメント統合や順序調整を行い、`cam_sim` は最適化後の経路だけを実行する
- ステップ実行中の機械制約再検証
  - 例: ロータリ軸角度や姿勢補間結果が `MachineConstraint` を満たすかを `cam_algorithms::machine_validation` に問い合わせる
- 再生品質向上のための事前干渉チェック
  - 例: シミュレーション本体は切削除去量を担当し、ホルダ干渉や退避不足の判定だけを `cam_algorithms::collision_avoidance` に委譲する

**設計上の整理**:

- `cam_sim` が直接持つべきなのは時間進行、除去量更新、結果キャッシュ
- 経路の改善、実行前検証、干渉判定ロジックは `cam_algorithms` に集約する
- そのため `cam_sim -> cam_algorithms` は「実行前後の問い合わせ」に限定し、シミュレーション状態そのものは渡さない

```
│              └────┬────┘         ┌─┘              │

│              [アルゴリズム]    [表示]            │

```

### 依存方向の規則表

| From | To | 許可 | 備考 |
|------|-----|-----|------|
| `cam_core` | `cam_algorithms` | ❌ | データ基盤は逆依存のみ |
| `cam_core` | `cam_sim` | ❌ | シミュレーション層への依存不可 |
| `cam_core` | `cam_entity` | ❌ | 表示層への依存不可 |
| `cam_algorithms` | `cam_core` | ✅ | **正向依存OK** |
| `cam_algorithms` | `geo_algorithms` | ✅ | 幾何アルゴリズムへの依存OK |
| `cam_algorithms` | `cam_sim` | ❌ | シミュレーション層への依存不可 |
| `cam_algorithms` | `cam_entity` | ❌ | 表示層への依存不可 |
| `cam_sim` | `cam_core` | ✅ | データ読み取りOK |
| `cam_sim` | `cam_algorithms` | 🔶 | **限定的 OK**（*1） |
| `cam_sim` | `cam_entity` | ❌ | 直接依存は避ける |
| `cam_entity` | `cam_core` | ✅ | データ読み取りOK |
| `cam_entity` | `cam_algorithms` | ❌ | 存在しない関数呼び出し |
| `cam_entity` | `cam_sim` | ✅ | シミュレーション読み取りOK |

*1: `cam_sim -> cam_algorithms` について

- **許可理由**: ツールパス再検証、干渉チェック再実行など、シミュレ中にアルゴリズムが必要な場合がある
- **制約**: 逆依存（`cam_algorithms -> cam_sim`）は厳禁
- **運用**: インターフェイスは最小化。FAT ファンクション は避ける

## 3️⃣ CAM層と geo_* 層の境界ルール

### 原則

```
┌──────────────────────────────────┐
│  geo_* 層                        │
│  （汎用幾何演算・アルゴリズム）  │
└──────────────────────────────────┘
         ↑ 依存 (OK)
         │
┌──────────────────────────────────┐
│  cam_* 層                        │
│  （CAM固有ロジック）            │
└──────────────────────────────────┘
         │ 依存 OK
         ↓
[アプリケーション層：viewmodel etc]
```

### 具体規則

| 事項 | ルール |
|------|--------|
| **Shape 型参照** | CAM層は `geo_primitives` / `geo_nurbs` の形状を自由に使用可 |
| **アルゴリズム呼び出し** | `geo_algorithms` の関数を `cam_algorithms` から呼び出し可。`cam_core` からは呼び出し不可 |
| **Trait 実装** | CAM固有のtrait（例: `CamSpecificProperty`）は `cam_core` / `cam_algorithms` 側で定義。geo側は拡張不可 |
| **逆依存** | **厳禁**: `geo_*` 層から `cam_*` への依存は一切不可 |

ファイル: `scripts/check_architecture_dependencies.ps1`

**拡張対象**:

- 上記「依存方向の規則表」をスクリプトで検証可能な形に記述

**単なる許可表追加以外に必要な作業**:

- `scripts/_arch_rules_data.ps1` の `ARCH_LAYER_MAPPING` に `cam_algorithms` を追加する
- `scripts/_arch_rules_data.ps1` の `ARCH_LAYERS` に `cam_algorithms` を Model 層として追加する
- `scripts/_arch_rules_data.ps1` の `ARCH_ALLOWED_DEPS` に `cam_algorithms` 自身の許可依存と、既存クレート側の `cam_algorithms` 許可有無を反映する
- `scripts/_arch_rules_data.ps1` の `ARCH_FORBIDDEN_DEPS` に `cam_algorithms` を含む禁止方向を反映する
- 必要なら `ARCH_REQUIRED_MODEL_CRATES` に `cam_algorithms` を追加し、新設後は存在必須クレートとして扱う
- `dev/architecture/ARCHITECTURE.md` 側の層構成説明も同時更新する

**重要な整理**:

- `check_architecture_dependencies.ps1` 本体は共有ルールデータを読むだけなので、主変更点は `scripts/_arch_rules_data.ps1`
- つまり「cam_algorithms 追加時はスクリプト反映が必須でセット実施」という認識で正しい
- さらに実運用では、workspace 参加、設計ドキュメント更新、依存ルール更新を同一変更セットに含める必要がある

**実装例** (pseudo-code):

```ps1

    "cam_algorithms -> cam_core",
    "cam_algorithms -> geo_algorithms",
    "cam_sim -> cam_core",
    "cam_sim -> cam_algorithms",  # 限定的（注記）
    "cam_entity -> cam_core",
    "cam_entity -> cam_sim",
)

$forbidden = @(
    "cam_core -> cam_algorithms",
    "cam_core -> cam_sim",
    "cam_core -> cam_entity",
)
```

## 7️⃣ 2D/2.5D優先のToolPath方針（2026年3月29日合意）

本節は、Issue #504（PathGeometry拡張）に着手する前に固定すべき前提を記録する。

### 7.1 前提

- 2D/2.5D加工は、3D/5軸より幾何表現が単純でも、加工意図・固定サイクル・制御機差分の取り扱いが複雑になりやすい
- 仕様変更は CAM計算と切削シミュレーションの両方へ波及するため、実装着手前の方針固定を必須とする
- v0（未リリース）運用のため、現時点では破壊的変更を許容する

### 7.2 先に固定する責務分離

ToolPathの複雑化抑制のため、以下を分離する。

- OperationKind（加工意図）
  - 例: Contour, Pocket, DrillCycle, FaceCycle, DeepDrillCycle, ThreadCycle
- PathGeometry（幾何表現）
  - 例: Line, Arc, Helix, PlanarSpiral
- PostMapping（制御機依存写像）
  - FixedCycleKind/variant を CNCコントローラー向け G-code へ変換

### 7.3 PathGeometry分類ルール（誤正規化の防止）

- Arc: 半径一定、中心一定の円弧
- Helix: 半径一定 + Z連続変化
- PlanarSpiral: 半径が連続変化する平面螺旋（Z一定を許容）

注意:

- PlanarSpiral は Arc へ正規化しない
- `delta_z == 0` は Arc と同値ではない
- XY平面で穴径を広げる螺旋切削は PlanarSpiral として保持する

### 7.4 固定サイクルの位置づけ（PoC対象）

- 固定サイクルはポスト処理に直結するが、アプリケーション層/モデル層では制御機非依存の正規化表現を保持する
- Fanuc系の呼び分け（例: G181/G182/G183/G184、variant）を想定しつつ、cam_core側は canonical な種別を優先する
- マクロ挿入は商用要件として認識するが、当面は凍結する

### 7.5 #504 PoCの最小受け入れ条件

- [ ] OperationKind と PathGeometry を分離した最小データ構造を定義できる
- [ ] PathGeometry に Arc/Helix/PlanarSpiral を独立表現として追加できる
- [ ] 固定サイクルの canonical 種別（最低4種）を保持できる
  - Drill
  - Face
  - DeepDrill
  - Thread
- [ ] controller profile を切り替えて fixed cycle を写像できる設計を示せる
- [ ] マクロ挿入を凍結したまま将来拡張点を確保できる

### 7.6 実装前に決める最終論点

- fixed cycle の初期採用種別（4種で開始するか）
- パラメータ必須項目（R/Z/Q/P/F 等）の最小セット
- variant の表現（String許容か、enum化するか）

上記3点の合意を、Issue #504 の実装開始条件とする。

## 8️⃣ #684 CAMソルバー最小導線契約（Option A / Step A）

本節は Issue #684 の設計固定を目的とし、実装前提となる最小契約を定義する。

### 8.1 目的

- 形状データ（NURBSを含む）入力から ToolPath artifact を生成し、`NcPostFromCam` へ接続可能な最小導線を固定する
- `JobType + InputRef -> ResultRef` 契約を維持したまま、solver 導線を明文化する

### 8.2 入力モデル（最小）

最小入力は `InputRef`（solver 入力を指す参照）が指す payload とし、以下を必須項目とする。

- `geometry_kind`
  - `nurbs_surface_set`（#684 で実装）
  - `triangle_mesh`（#684 で実装。離散化済みポリゴン入力、STL 等）
  - `nurbs_curve_set`（未実装。2D/2.5D 輪郭系として #212 で扱う）
  - `curve_chain_2p5d`（未実装。同上）
- `tool_id`
- `operation_id`
- `units`
- `coordinate_frame`

補足:

- solver は `InputRef` 参照先を解決して入力を復元する
- `cam_sim` 側で参照解決するが、Job Manager は payload 本体を解釈しない

### 8.3 solver 最小責務

- 入力契約の検証
- ToolPath 生成（最小形）
- 失敗分類の返却
  - `invalid_input`
  - `no_solution`
  - `convergence_failure`
- 生成結果を `toolpath` artifact binary v0.1 に接続

非責務（本Issueの非スコープ）:

- 加工時間最小化などの高度最適化
- コントローラ固有 post 最適化
- UI編集機能

### 8.4 最小導線シーケンス

1. `JobType::CamProcess` で `InputRef` を受理
2. `InputRef` から solver 入力を復元
3. solver を実行して ToolPath を生成
4. `toolpath` artifact binary v0.1 として永続化
5. `ResultRef` を返却し、後続 `NcPostFromCam` が参照する

### 8.5 失敗分類と契約境界

- 状態異常（入力契約エラー）: `invalid_input`
  - 必須項目欠落、型不一致、units/frame 不整合
- 状態正常だが解なし: `no_solution`
  - 入力契約は妥当だが、幾何制約下で有効経路を構築できない
- 内部計算異常（数値解法エラー）: `convergence_failure`
  - 入力契約は妥当だが、反復解法が収束条件を満たさない

補足:

- `convergence_failure` は `invalid_input` とは別分類として扱う

いずれも Job Manager には失敗種別のみ伝達し、幾何計算の内部状態は公開しない。

- #680-#683: NC post 拡張系列は、本節で固定した solver->toolpath 導線を前提とする

### 8.7 本番導線シナリオ（Job Manager 経由）

`model/application` / `model/job_runtime` / `model/cam_sim` の本番導線を対象に、以下を最小受け入れシナリオとする。

1. 正常系: CAM親ジョブ -> 切削シミュレーション子ジョブ
  - `CamProcess` が `toolpath` artifact を生成し、`CuttingSimulation` が親 `ResultRef` を参照して成功する
  - 成功時に `status=succeeded`、`result://sim/<id>/ok`、`log://sim/<id>/ok` を返す

2. 異常系: 入力契約不正（invalid_input）
  - 必須項目欠落、units/frame 不整合、`InputRef` 形式不正のいずれかで失敗する
  - Job Manager へは `invalid_input` として集約した失敗分類を返す

3. 異常系: 経路未生成（no_solution）
  - 幾何制約により有効 ToolPath を構築できない入力で失敗する
  - Job Manager へは `no_solution` として失敗分類を返す

4. 異常系: 収束失敗（convergence_failure）
  - 入力契約は妥当だが、反復解法が収束閾値を満たさない場合に失敗する
  - Job Manager へは `convergence_failure` として失敗分類を返す

5. 契約境界系: 親子制約違反
  - `CuttingSimulation` の `parent_job_id` 欠落、または親IDと `input_ref` の不一致で reject する
  - `JobType + InputRef -> ResultRef` 契約を壊さず、内部詳細は公開しない

1. 入力契約モデルと失敗分類マッピングの固定
2. CAM親ジョブから `toolpath` artifact 生成導線の最小実装
3. 切削シミュレーション子ジョブでの `ResultRef` 参照実行
4. 上記 8.7 の 5 シナリオをテストで固定

### 8.9 実装（#684 完了時点）

配置:

- `model/cam_algorithms`: solver 本体（純粋計算）
  - `solver`: 入力契約 `CamSolverInput`、失敗分類 `CamSolverError`、入口 `solve_toolpath`
  - `tessellation`: 三角形の形状品質（アスペクト比）

  - `inverse_offset`: 工具の形（`CutterShape`）と、製品形状の三角形の準備・XY の升目の索引
  - `inverse_offset_shape`: 逆オフセット形状（`InverseOffsetShape`。8.11）と、その上側の面からの工具先端の高さ
  - `scanline`: `operation_type = scanline` の経路化
- `model/cam_sim`: Job アダプタと参照解決
  - `CamSolverInputProvider`: `InputRef` → `CamSolverInput` の解決境界
  - `InMemoryCamSolverInputStore`: プロセス内 provider 実装（`input://cam/<name>` のみ受理）
  - `CamJobExecutorAdapter::with_input_provider`: provider 接続済みアダプタ

3D 経路生成方式（逆オフセット法）:

- 形状を三角形へ離散化し、各要素を工具形状で逆オフセットした面の上側包絡を工具中心高さとする
- 出力は工具先端（ToolPath 座標）の高さとする
- 凹辺のオフセットは他要素の包絡に覆われるため全辺を評価しても結果は変わらない（凸辺限定は #256 の高速化対象）

工具種別ごとの要素オフセット:

| 工具 | 頂点 | 辺 | 面 | 対応 |
|------|------|----|----|------|
| ボールエンドミル（半径 r） | 球（中心高さ − r が先端） | 円筒（円弧掃引面） | 法線方向 r オフセット平面 | #684 |
| フラットエンドミル（半径 r） | 円板（頂点高さ） | 円板掃引（水平距離 r 以内の辺上最高点） | 底面円周接触（最大傾斜方向へ r 進んだ点） | #684 |
| ラジアスエンドミル（半径 R・コーナー r） | トーラス | トーラス掃引（数値解法） | オフセット面 | #211 |

- いずれも閉形式で解けるボール/フラットを #684 の範囲とし、辺で数値解法を要するラジアスエンドミルは #211 で扱う
- 未対応工具（ラジアスエンドミル）は `invalid_input` を返す

失敗分類の決定箇所:

| 分類 | 決定条件 |
|------|----------|
| `invalid_input` | `InputRef` 形式/ドメイン不正、必須項目欠落、値域外（stepover > 工具径等）、未対応工具、provider 未登録（本番ビルド） |

| `convergence_failure` | 離散化の弦誤差が `chord_tolerance` 以内に収束しない（再分割反復上限・頂点数上限超過） |

### 8.10 逆オフセット包絡面のデバッグ表示

逆オフセットの結果を目視確認するため、包絡面（CL 面）を表示するデバッグ機能を持つ。

| 層 | 配置 | 責務 |
|----|------|------|
| Model | `cam_algorithms::cl_grid`（`sample_cl_grid`） | 逆オフセット形状を等間隔格子で評価し工具先端高さを返す |
| Application | `application::cam_inspection`（`inspect_inverse_offset`） | 形状離散化・包絡面評価を束ね、基準点高さ（ボール: 球中心、フラット: 底面中心）の格子を返す |
| ViewModel | `viewmodel::inverse_offset_converter` | 表示モードに応じてシェーディングメッシュと重畳線分へ変換する |
| View | `view/app` の `debug_scene::inverse_offset` | キー操作で表示・切替する |

- 入力形状はサンプル NURBS 曲面（`m` キー表示と同一）、弦誤差はアプリの表示トレランスを用いる
- 評価範囲は形状の XY 範囲を工具半径だけ広げた領域とし、外周で工具が接触する範囲も表示する
- 表示モード
  - 包絡面: 包絡面をシェーディング表示し、元形状を三角形エッジで重畳する
  - 格子線: 元形状をシェーディング表示し、包絡面を一定ピッチ（評価間隔 × 格子線間隔）の格子線で重畳する
- 接触境界（工具が形状に触れ得る範囲の外縁）
  - Model 層で、接触あり/なしが切り替わる格子辺ごとに二分法で境界点を求める（停止条件は既定の距離トレランス）
  - 両モードで境界を輪郭線として重畳し、境界を跨ぐ格子セル・格子線は境界点まで切り詰める
  - 形状の角の外側では、工具が触れ得るのは角頂点のみのため、包絡面は角頂点を中心とする半径 r の 1/4 円で丸まる（欠けではなく幾何的に正しい形状）
- キー操作: `i` 表示、`Shift+I` 工具切替（ボール/フラット）、`g` 表示モード切替

### 8.11 逆オフセット形状（#1016）

工具を逆さまにして製品形状の上で掃引した形を、製品形状の三角形メッシュの面・頂点・辺を工具の形でオフセットした要素の集まりとして持つ（`InverseOffsetShape`）。その上側の面が CL の面で、工具先端の高さは、(x, y) の鉛直線と要素の交点のうち最も高い点から求める。工具は 3 次元の向きのオフセット r2 と径の向きのオフセット r1 に分けて扱う（ボールは r1 = 0、フラットは r2 = 0。ラジアスは後続）。

| 要素 | ボール（半径 r2） | フラット（半径 r1） |
|---|---|---|
| 面 | 外向きの法線の向きに r2 ずらした三角形 | 外向きの法線を水平面に射影した向きに r1 ずらした三角形 |
| 頂点 | 球面のうち、つながる辺に垂直な平面（頂点を通る）の、辺と反対の側の部分 | 範囲に真上の向きがある（工具の底が乗る）頂点だけ、頂点の高さの水平な円板 |
| 辺 | 円柱面のうち、軸への垂線の足が辺の中にあり、軸から離れる向きが隣り合うどの面の側にも向かない部分 | 水平な円板の縁を辺に沿って動かした形（斜円柱）のうち、隣り合う面ベクトルの間の向きで接する部分（XY に投影した辺と、(x, y) を中心とする半径 r1 の円の交点のうち、範囲にある点の高さ） |

- 要素は式と範囲で持ち、三角形に分けない。土台の面は geo_primitives の型（`Triangle3D`・`SphericalSurface3D`・`CylindricalSurface3D`・`Circle2D`）で、鉛直線との交点は geo_algorithms の交差演算（`CrossIntersection`）で求める。範囲は、トリムした面のエンティティではなく、逆オフセット法の条件として cam_algorithms が持つ
  - 円柱面と半直線、線分と円の交差を geo_algorithms に加えた（線分と円は内部の関数を公開した）。球面・円柱面と半直線の交点は、始点から最も近い点と中心（軸）までの距離を先に求め、√(r² − h²) で求める（工具の半径が始点の距離より桁違いに小さくても、r² が桁落ちで失われない）
- 形状ポリゴンの位相化: 三角形メッシュの隣接（辺ごとの三角形・頂点につながる辺）と三角形の向きをそろえること（`TriangleMeshAdjacency::orient`。塊ごとに、面がちょうど 2 つの辺で 2 つの三角形が辺を逆の向きにたどるようにする）は geo_algorithms、外の決め方と外す要素の判定は cam_algorithms
  - 外（材料のない側）は、塊の中の、上から届く面（上側の包絡に出ている面）が上を向く向きとする。STL の頂点の順は外向きとは限らないため（サンプルデータは向きがそろっているが 97% の面が下向き）、形から決める。塊の三角形は、逆オフセット形状の中の写しで頂点の順を入れ替える（入力のメッシュは書き換えない）。以後の法線は外積のまま外向き
  - 向きをそろえられない塊（メビウスの帯のような）と、上から届く面がない塊は外を決められないため、面ごとに上向きにそろえ、辺・頂点を外さない
  - 外向きの法線で凹か平らな辺を外す（一方の面の外向きの法線で、もう一方の面の辺にない頂点が平面の外の側になければ凹か平ら）。工具の向きによらず、鉛直な面も判定できる。わずかでも凸の辺は残す。凸の辺の両側の面の要素は辺から離れる向きにずれ、間を辺の要素が埋める。フラットは面ごとに工具の半径だけずれるため、ほぼ平らな凸の辺でも間が 2 × r1 開く（サンプルデータで、角の許容誤差の分だけ平らな凸の辺を外したところ、工具が接しない点が出た）
  - 縁でなく、つながる辺がすべて外した辺の頂点を外す。縁の辺・3 つ以上の面の辺は残す
  - 外した要素は隣り合う面の要素に覆われ、逆オフセット形状の面に出ない（外す前と後の高さの一致をテストで確かめる）
  - 開いた塊（縁の辺か 3 つ以上の面の辺がある塊）で下を向く面に隣り合う辺は外さない。開いた面は両側から工具が届くことがあり、面の上側から見ると凹凸が逆になるため
  - 辺の範囲は、辺から面の内側へ向かう向き（面の 3 つ目の頂点で決まる）で決める。凸の辺では、資料の「隣り合う面の法線の間」と同じ範囲
  - フラットの頂点・辺も、資料どおり範囲に限る（#1020）。工具は上から近づくため、工具の底の縁が辺の点に接するのは、隣り合う面ベクトルの間（辺に垂直で、どの面の内側へも向かない向き w）に、水平な成分が辺の点から (x, y) への水平な向き h の向きで、下を向かないものがある場合。辺の向きを a（a_z ≥ 0）、面の内側への向きを t とすると、その w は (a_z h, −h·a) の向きのため、条件は h について線形の h·(a_z t − t_z a)_xy ≤ 0 と h·a_xy ≤ 0（h は下りの向き）になる。水平な辺で範囲に真上の向きがある場合（尾根）は、工具の底が辺に乗るため全周を範囲にする
  - フラットの頂点は、範囲に真上の向きがある場合だけ工具の底が頂点に乗り、円板を持つ。それ以外の範囲は、工具の底の縁が頂点に接する円弧（面積がない）で、つながる辺の要素の端と同じため外す（資料の「切り取った球面を径方向にオフセット」で r2 = 0 とした形）
  - 範囲に限る前と後で、サンプルデータの工具先端の高さは一致し（210 万点で差 0）、工具の底の円の内側の最も高い点を総当たりで求めた高さとも一致する（テスト）
  - 上を向かない面（鉛直な面・アンダーカットの面）の要素は、外向き（アンダーカットでは下向き）に正しくずらして持ち、高さを求める索引には入れない
  - 閉じた塊の下を向く面は、真上に塊の材料と上を向く面があり、上から届かない。開いた塊の下を向く面は、一部が上から見えることがある（例: 上面より外にはみ出した張り出しの下の面）ため、上側（外向きと逆の向き）にずらした要素も索引に入れる。工具を上から下ろして最初に当たる高さは、すべての面の要素の高さの最大と同じため、隠れている面の上側の要素は上から先に当たる面より低く、高さを変えない
- 鉛直線を表す半直線の始点は、要素ごとに、その要素の最も低い点のすぐ下に置く（メッシュ全体や、同じ点で調べる要素の中の最も低い点を始点にすると、離れた低い形状や真下の低い形状の高さで、交点の高さが桁落ちする）
- 要素は、決める高さの上限（面は三角形の最も高い頂点、ボールの頂点・辺は最も高い点 ＋ r、フラットの頂点・辺は最も高い点）の高い順に並べてから索引に入れ、升目の候補もこの順にする。それまでの最も高い点が次の候補の上限以上になった時点で評価を打ち切る（#912）。残りの候補はそれより高くならないため結果は変わらず、面の向き（外を決められない塊・開いた形）にもよらない。サンプルデータで、打ち切りの有無の高さは 210 万点で一致し、1 点の時間はボール 4.6 µs → 3.7 µs（−20%）、フラット 4.2 µs → 3.7 µs（−12%）（同じ計算機で交互に 2 回ずつ測った値）
- 三角形と半直線の交点は、面の中での辺までの距離が許容誤差の中なら三角形の中とする（同じ平面の三角形が共有する辺の上の点を、丸め誤差で両方が外さない。半直線の向きから見た距離で判定すると、急な面で三角形から大きく外れた点を受け入れる）
  - 面（NURBS・B-rep）で入力する場合は、面の表裏（モデラーの向き）をそのまま使い、向きをそろえて外を決める処理は STL のときだけ行う（後続）
- 形状はジョブから独立したメモリの中のデータとし、工程ごとに作る（工程の間では共有せず、外部ファイルにしない）
- ツールパス生成と同じ形状・工具で逆オフセット形状を作る入口は `build_inverse_offset_shape`（`solve_toolpath` も使う。デバッグ表示が、CL の計算と同じ形を見せるため）
- 表示用の三角形（`InverseOffsetShape::display_parts`。表示・保存だけに使い、計算には使わない。#1017）
  - 要素の役割ごとに分ける: 高さを求める索引に入る面／入らない面（鉛直な面・アンダーカットの面）／開いた塊の下を向く面の上側の要素／外を決められなかった塊の面／頂点／辺
  - 球面・円柱面・円板は角度のきざみ（1° から 90°）で分ける（全体の許容誤差で分けると、サンプルデータで三角形が数百万になる）。範囲は正確に切り取る: 球面は、正二十面体を細かく分けた三角形を範囲の平面（球の中心を通る）で切り取ってから球面へ戻し、円柱面は範囲を円弧として求める（ほぼ平らな凸の頂点・辺の範囲は、きざみより狭い）
  - 面の役割（索引に入るか、外を決められなかった塊の面か）は、作るときに面ごとに持つ（表示で判定し直すと、境目で計算と食い違う）
  - フラットの辺は、円板の縁のうち範囲の円弧を、辺の点の高さのまま辺に沿って動かした面（斜円柱の一部）。範囲に限ったことで、サンプルデータ（きざみ 10°）のフラットの三角形は 75.2 万から 15.1 万に減った（1 点の高さを求める時間は 3.46 µs から 3.22 µs）
  - 表示用の三角形は要素の面の弦のため、上側の面より上に出ない。弦と面の隔たりは、面に垂直な向きに r × (1 − cos きざみ) 以下のため、鉛直な向きでは、上側の面の傾き s の点で √(1 + s²) 倍以下になる（テストで確かめる）

測定（サンプルデータ 3.8 万三角形、工具の半径 5 mm、ピックフィード 2 mm の走査線の上を 0.1 mm ごとに 210 万点、release）:

| | 以前の実装（三角形ごとに頂点・辺・面をすべて評価） | 逆オフセット形状 |
|---|---|---|
| ボール: 作る時間 / 1 点 | 0.010 s / 4.02 µs | 0.063 s / 3.79 µs |
| フラット: 作る時間 / 1 点 | 0.010 s / 3.94 µs | 0.069 s / 3.35 µs |
| 以前の実装との高さの差 | — | ボール: 1 点で 1.1 × 10⁻⁹ mm（丸め）、フラット: 10⁻⁹ mm 未満 |

## 9️⃣ #689 工程テンプレート精度プロファイル運用契約（Step A）

本節は Issue #689 の設計固定を目的とし、加工ステージ別オペレーションと精度プロファイル適用契約を定義する。

### 9.1 精度プロファイル

- `press_rough`: 0.001mm
- `mold_finish`: 0.0001mm

`tolerance_profile` の適用優先順位:

1. オペレーション定義の `tolerance_profile` 明示指定
2. 工程テンプレートの `tolerance_profile` 既定値
3. solver の `tolerance_profile` 既定値

### 9.2 `operation_type` 決定規約

`operation_type` で受理する canonical token は以下に固定する。
実装・保存・artifact 追跡では、別名や自然言語ではなくこれらの token を用いる。

- `contour_offset`
  - 等高線オフセット加工。荒加工での外周からの段階切込み、およびストック入力ありの等高線オフセット加工を含む
- `rest_machining`
  - 等高残加工。前工程や大径工具で残った未加工領域を小径工具などで追い込む加工
- `scanline`
  - スキャン加工。一定方向の往復または片方向走査で面を仕上げる加工
- `surface_follow`
  - 面沿い加工。対象面の法線・曲率・パラメトリック流れに追従して経路を生成する加工

`operation_type` の適用優先順位:

1. `operation_type` 明示指定
2. 工程テンプレートの `operation_type` 既定値
3. solver の `operation_type` 既定値

加工の種類の足し方（#1049 で決めた）:

- 加工の種類は、trait で抽象化せず、加工の条件の値の enum（`cam_core::OperationSpec`）に種類ごとの variant と条件の型を足す。種類は RedRing の中で作るもので、外から足す仕組みは要らない。条件は保存・比較・複写・画面での編集に使う値として持ち、種類を足したときの対応の漏れは `match` のコンパイルエラーで見つける
- どの種類の工程も持つ項目（工具・加工領域・精度プロファイル・加工の段階・送り）は、variant の外の工程の項目にする。送りは今は走査線の条件の中にあり、ツールライブラリ（#887）か 2 つ目の加工の種類のときに外へ出す
- 経路の作り方は、種類ごとに 1 ファイル（スキャン加工は `scanline.rs`）に置き、`solve_toolpath` の `match` で振り分ける。逆オフセット形状・加工範囲の決め方などの共通の計算は、種類のファイルの外の関数にする。大きくなった種類は、ディレクトリに分ける
- 2 つ目の加工の種類を足すときに、`solver.rs` に残るスキャン加工専用のもの（走査線の条件の検証と、工具の移動範囲による範囲の決め方）を `scanline.rs` へ移すか、共通にするかを決める。また、token の解決用の `OperationType` と `OperationSpec` をまとめられるかを見直す

### 9.3 加工ステージ別オペレーション

`machining_stage` は実行順序を強制するための状態ではなく、工程テンプレート上のタグ分類として扱う。

- 荒加工（rough）
  - 等高線オフセット加工（`contour_offset`）
- 中加工（semi_finish）
  - ストック入力あり等高線オフセット加工（`contour_offset`）
  - 等高残加工（`rest_machining`）
- 仕上げ（finish）
  - スキャン加工（`scanline`）
  - 面沿い加工（`surface_follow`）
  - 小径工具による等高残加工（`rest_machining`、等高中加工後の追い込み用途）

補足:

- 等高残加工は `semi_finish` を基本配置とするが、小径工具での追い込み時は `finish` でも許容する
- `machining_stage` タグと `operation_type` の組み合わせで運用し、単純な前後関係だけで reject しない
- `machining_stage` と `operation_type` は直交する属性とし、`finish` だから常に `surface_follow` になる、といった自動推論は行わない

### 9.4 加工範囲指定方式

- `edge_projected_2d`
  - エッジ指示を加工方向へ投影した2D境界を使用
- `rectangle`
  - 矩形座標値（min/max）を直接指定

入力契約（最小）:

- `operation_type`
- `machining_stage`
- `boundary_mode`
- `machining_direction`
- `tolerance_profile`
- `stock_ref`（`machining_stage = semi_finish` かつ `operation_type = rest_machining` の時に必須）

必須フィールド制約:

- `machining_direction`
  - canonical token: `+X` / `-X` / `+Y` / `-Y` / `+Z` / `-Z`
  - 単位なしの軸方向指定として扱い、角度値や任意ベクトルは受理しない
- `boundary_mode = edge_projected_2d`
  - `edge_refs`（1件以上）を必須とする
  - `edge_refs` を `machining_direction` へ投影して2D境界を構築できない場合は失敗分類とする
- `boundary_mode = rectangle`
  - `rect_min=(x_min,y_min)` と `rect_max=(x_max,y_max)` を必須とする
  - 座標系はワーク局所座標、単位は mm 固定とする
  - `x_min < x_max` かつ `y_min < y_max` を満たさない場合は失敗分類とする
- `tolerance_profile`
  - 許容値は `press_rough` / `mold_finish` のみとする
  - 未指定は `missing_tolerance_profile`、未知値は `invalid_tolerance_profile` として失敗分類する
- `operation_type`
  - 許容値は `contour_offset` / `rest_machining` / `scanline` / `surface_follow` のみとする
  - 別名 token の導入は許可しない

### 9.5 失敗分類（初期・内部分類）

- `invalid_tolerance_profile`
- `missing_tolerance_profile`
- `unit_mismatch`
- `boundary_projection_failed`
- `empty_projected_boundary`
- `operation_boundary_out_of_domain`
- `stock_required_but_missing`

失敗分類マッピング:

- 本節の列挙はテンプレート適用段階の内部分類であり、Job Manager へ直接公開する分類コードではない
- Job Manager へ返す失敗分類は #684 で定義済みの 3 分類（`invalid_input` / `no_solution` / `convergence_failure`）に統一する
- #689 で追加した内部分類は以下へ集約する
  - `invalid_tolerance_profile`
  - `missing_tolerance_profile`
  - `unit_mismatch`
  - `boundary_projection_failed`
  - `empty_projected_boundary`
  - `operation_boundary_out_of_domain`
  - `stock_required_but_missing`
  - 上記はすべて `invalid_input` へマップする

### 9.6 責務境界

- Job Manager はテンプレート本体を解釈せず、`InputRef` / `ResultRef` 契約を維持する
- Model/CAM 側がテンプレートを解決し、profile と operation を solver へ適用する

### 9.7 工程順序ポリシー

- 工程順序チェックは設定可能な警告として扱う（既定は warning、hard error にはしない）
- 例: `finish` が `semi_finish` より先行する場合、設定有効時に警告を出す
- 警告出力の有無はテンプレート設定で制御し、`JobType + InputRef -> ResultRef` 契約は維持する

### 9.8 実装（Step B/C）

配置:

- `cam_core::tolerance`: 精度プロファイル `ToleranceProfile`（`press_rough` / `mold_finish`）と加工トレランス定数
  - 数値カーネルの判定トレランスではなく CAM の加工精度のため、既存の CAM トレランス（`CamTolerance`）と同じ場所に置く
- `cam_algorithms::process_template`: 工程テンプレートの解決と solver への適用
  - `resolve_operation(template, operation, defaults)`: 優先順位に従い `tolerance_profile` / `operation_type` / `machining_stage` / 加工範囲を解決
  - `build_solver_input(resolved, ...)`: 解決結果を `CamSolverInput` へ適用（`chord_tolerance` = プロファイルの加工トレランス）
- `CamSolverInput.boundary`: 加工範囲（未指定なら、走査線の条件の工具の移動範囲 `ScanlineParams::tool_range` に従う）

優先順位の解決規則:

- 明示指定 → 工程テンプレート既定値 → solver 既定値（`SolverDefaults`）の順に最初の指定を採用する
- 採用した token が未知の場合は下位の既定値へ落とさずに失敗する
- `SolverDefaults` の初期値は未設定とし、どこにも指定がなければ `missing_tolerance_profile` / `missing_operation_type` とする（精度の暗黙適用を防ぐ）

内部分類の追加（§9.5 の列挙に対する実装上の追加。いずれも `invalid_input` へ集約）:

| 内部分類 | 条件 |
|----------|------|
| `invalid_operation_type` | `operation_type` が canonical token 以外 |
| `missing_operation_type` | `operation_type` がどこにも指定されていない |
| `invalid_machining_stage` | `machining_stage` が `rough` / `semi_finish` / `finish` 以外 |
| `invalid_rectangle_boundary` | 矩形が `x_min < x_max` かつ `y_min < y_max`（有限値）を満たさない |
| `unsupported_operation_type` | token は正しいが solver が未対応（現状 `scanline` 以外） |

`invalid_input` の reason は先頭を `<内部分類>` とし、詳細がある場合のみ `<内部分類>: <詳細>` とする（`missing_*` や `operation_boundary_out_of_domain` のように詳細を持たない分類もある）。判定は先頭の内部分類で行い、Job Manager へは分類コード `invalid_input` のみを伝達する。

加工範囲を指定しない場合の工具の中心の移動範囲（`ScanlineToolRange`、#940）:

- `ExtendByToolRadius`（既定値）: 形状の XY 範囲を、各辺で工具の半径だけ外へ広げた範囲（reach）。工具の中心が形状の端までしか行かないと、ボールエンドミルの断面の形により平坦面の端の外側の素材が残るため、これを既定とする
- `GeometryExtent`: 形状の XY 範囲
- 形状の外へ出た工具は、逆オフセットのとおり形状の端の稜線に触れる位置まで下がり（ボールは稜線の上を転がる）、製品形状には食い込まないが、端の外側の素材を丸く削る（角がだれる）。角をだれさせない場合は、見切り面を加工の対象に含める運用とする（面を仮想的に延ばす処理は持たない）

スキャン加工の送り方（`ScanlineCutDirection`、#994）:

- 主軸は右回り（上から見て時計回り）に固定する。主軸の回転方向をどこに持つか（工具か機械の条件か）は、工程の条件を整理するときに決める
- 走査ラインは Y 正方向へ進むため、まだ削っていない素材は各ラインの +Y 側にある。X 負方向に送ると素材が送りの右側になってダウンカット、X 正方向に送るとアップカットになる
- `DownCut`（既定値）: すべてのラインを X 負方向に送る。ツールパスの切削方向は `Down`
- `UpCut`: すべてのラインを X 正方向に送る（#994 より前の加工）。ツールパスの切削方向は `Up`
- `ZigZag`: 最初のラインをダウンカット（X 負方向）で送り、ラインごとに向きを入れ替える。1 本のラインが形状との接触で複数のパスに分かれても、ラインの中のパスは同じ向きで、送る順に並べる。ツールパス全体の切削方向は 1 つの値に決まらないため `Mixed` とする（artifact の形式は v0.2。`ARTIFACT_BINARY_IO_CONTRACT_DESIGN.md`）
- 削られた後の素材の形は送り方によらない。切削シミュレーションは切削方向を使わない

矩形加工範囲（`boundary_mode = rectangle`）:

- 「形状の XY 範囲を工具半径だけ広げた領域」（reach）を工具が形状に触れ得る範囲とする
- 矩形を reach でクリップした結果が面積を持たない場合（重ならない、または辺・角で接するだけ。幅・高さが距離トレランス以下）は `operation_boundary_out_of_domain`（経路生成まで進めて `no_solution` にしない）
- 重なる場合は矩形を reach でクリップした範囲を走査する（形状外でも工具半径以内なら接触し得るため形状範囲では切らない。reach 外は接触し得ないため、過大な矩形でもサンプル数を形状規模に抑える）

後続 Step とする項目:

- `edge_projected_2d` と `machining_direction`（投影方向の解釈を含む）
- `stock_ref` と `stock_required_but_missing`（`rest_machining` の solver 対応と合わせる）
- 工程順序の警告（§9.7）
- `succeeded` 時の適用 profile / tolerance / operation_type の追跡メタデータ

計測（40mm 角の双二次ドーム、ボール R3、release ビルド）:

| プロファイル | 頂点数 | 三角形数 | 離散化 | 経路生成 |
|--------------|--------|----------|--------|----------|
| `press_rough` (0.001mm) | 28,561 | 56,448 | 80ms | 97ms |
| `mold_finish` (0.0001mm) | 263,169 | 524,288 | 633ms | 875ms |

`mold_finish` は頂点数・時間とも約 9 倍となる。経路生成は工具半径内の三角形数が支配的であり、#256（凸辺限定・要素絞り込み）の判断材料とする。計測は `profile_load_measurement`（`#[ignore]`）で再現できる。

## 🔟 #751 CAM テッセレーション品質制御（検証の結果、不採用）

本節は Issue #751 の検証結果と判断を記録する。

### 10.1 検証内容

CAM 用テッセレーション（テンソル積パラメータ格子、弦誤差のみで再分割）は、一方向にのみ曲がる形状で細長三角形を生成する。
品質条件（三角形アスペクト比の上限、最大辺長の上限）を試作し、効果と負荷を計測した。

アスペクト比 = 最長辺 / (2√3 × 内接円半径)（正三角形で 1。`cam_algorithms::triangle_aspect_ratio`）

一方向のみ曲がる 40×400mm の樋形状（ボール R3 のスキャン加工、release ビルド）:

| プロファイル | 品質条件 | 三角形数 | アスペクト比 最大 | 経路生成 |
|--------------|----------|----------|-------------------|----------|
| `press_rough` | なし | 512 | 369.8 | 21ms |
| `press_rough` | アスペクト比 ≤ 4 | 327,168 | 1.46 | 725ms |
| `press_rough` | 辺長 ≤ 工具半径 | 68,608 | 3.14 | 148ms |
| `mold_finish` | なし | 2,048 | 1,478.3 | 77ms |
| `mold_finish` | アスペクト比 ≤ 4 | 頂点数上限（100 万）超過 | — | — |
| `mold_finish` | 辺長 ≤ 工具半径 | 137,216 | 22.4 | 313ms |

2 方向に曲がるドーム形状（40mm）では、いずれの品質条件でも三角形数・アスペクト比は変化しなかった。

### 10.2 判断

- 細長三角形は逆オフセットの工具先端の高さの計算の性能を劣化させない。経路生成時間は三角形数が支配的で、品質制御なしが最速となる
- 逆オフセットは要素ごとに厳密に計算するため、細長三角形でも CL は形状の整った参照メッシュと弦誤差内で一致する（テスト `slivers_do_not_change_cutter_location`）
- CAM 精度でのアスペクト比制御は三角形数が数百倍となり、`mold_finish` では頂点数上限内に収まらない
- 以上から、CAM 用テッセレーションに品質条件は導入しない（試作した `max_aspect_ratio` / `max_edge_length` は破棄）
- 採用した変更は、各セルを短い方の対角線で分割すること（負荷なしで形状が改善する）と、品質指標 `triangle_aspect_ratio` の提供のみとする

### 10.3 CAE 向け高品質メッシュとの関係

- CAE で必要となる正三角形に近い要素品質は、テンソル積格子方式では構造上得られない（最良でも直角二等辺、アスペクト比 ≈ 1.39。パラメータのせん断も解消できない）
- トリム面、隣接面境界での辺共有、局所的な要素サイズ指定にも対応しない
- CAE 向けには、パラメータ空間での Delaunay 細分・前進波面法、または等方リメッシュ等の別アルゴリズムを、CAM/CAE から共用できる geo 層（または専用のメッシュクレート）に設計する

## 1️⃣1️⃣ #965 エアカットの計算の位置づけ

### 11.1 処理の順番

1. CAM の計算（工程ごとに CL を出す。エアカットは入れない）
2. CL の編集
3. 複数の工程をそろえる
4. エアカットの計算（安全な高さなど、形状と素材を使う）
5. ポスト処理（NC データに出力する。機械ごとの部分を加える）

### 11.2 判断

- CL の編集でパスの始まりと終わりが変わるため、エアカットを先に付けると編集のたびに付け直しになる。工程の間の移動・工具を替える前後の移動は、すべての工程がそろってから決まる
- 安全な高さと、エアカットが素材に当たらないかは、形状と素材の状態から決まるため、ポスト処理（機械を知り、形状を知らない）ではなく、ポスト処理の前の段階で計算する
- 早送りの動き方（G00 が直線にならない機械）・工具交換の位置・工具長補正など、機械ごとの部分はポスト処理で加える
- 走査線のツールパス生成は切削のパス（CL）だけを出し、パスの間の早送り・アプローチ・リトラクトを入れない。安全な高さ（`clearance_height`）は CAM の計算の条件から外した
- 切削アニメーションでは、パスとパスの間は工具を次のパスの始まりへそのまま移し、その間の移動を進捗の距離に数えない（切削シミュレーションは、経路が途切れるところの前後に時点を置く。#931）

### 11.3 測定（サンプルデータ、ボールエンドミル φ10、release）

| 項目 | エアカットあり | エアカットなし |
|------|----------------|----------------|
| 経路の距離 | 442.7 m | 227.3 m |
| 切削アニメーションのコマ数 | 90,344 | 46,669 |
| 最後の残りの体積 | 42,574,811.912 mm³ | 42,574,811.912 mm³（同じ） |

エアカットの計算の実装（安全な高さの計算・素材を使った短い移動）と、ポスト処理での NC データの出力は後続で扱う。

## 1️⃣2️⃣ #1015 スキャン加工の設計

スキャン加工（`operation_type = scanline`）を、加工として設計する。工具の中心の移動範囲（#940）・送り方（#994）・加工範囲（9.4）はそれぞれの節のとおりとし、本節では入力の役割と、CL の点の間の削り込みをトレランスに収める方法を決める。

### 12.1 前提

- 3 軸（工具の軸は +Z、工具は上から近づく）。工具はボール・フラット（ラジアスは後続）
- 逆オフセット形状（8.11）の上側の面が CL の面（工具先端が通る面）。CL の点はこの面の上にあり、点と点は直線でつなぐ
- 背景: #935 の比較で、サンプルデータ（ボールエンドミル φ10、ピックフィード 2 mm）の最も深い削り込みが、サンプル間隔 1.0 / 0.25 / 0.1 mm で 0.76 / 0.19 / 0.08 mm だった（壁の上の縁など）。点の上では CL の面に沿うが、点と点の間の直線が CL の面より下を通る。サンプル間隔にほぼ比例して小さくなるが、0.1 mm でもトレランス 0.001 mm に遠く、ジョブの時間は約 7 倍になる

### 12.2 Zmap の使い分け

Zmap（XY の格子点ごとの CL の面の高さ）は、参考資料（逆オフセット法と Zmap）では、CL の面の共通の表し方として、パスの作成（XY 平面で切って等高線、YZ・ZX 平面で切って走査線）、工具の突き出し長による領域分割、ポリゴンを使うそのほかの演算に使われている。逆オフセット法は、その格子点の値を求める方法として位置づけられている。

RedRing では、パスの形はトレランスを保証して逆オフセット形状から直接求め、範囲全体の判定・分類には Zmap を使う。

| 目的 | RedRing の対象 | 使うもの | 理由 |
|---|---|---|---|
| 走査線のパス | #1015（本節） | 逆オフセット形状で直接確かめる（12.4） | 点の間でトレランスを保証する必要がある |
| 等高線のパス | 等高線加工（後続） | 等高線の設計で決める | XY 平面で切るには Zmap が自然だが、急な壁では一定ピッチの精度が足りない。水平な平面で要素を直接切る方法や、XY・YZ・ZX の 3 つの直交格子の立方体の辺と CL の面の交点からマーチングキューブ法で CL の面を三角形にする方法（乾・崔、2002）と比べて決める |
| 工具の突き出し長による領域分割 | #947（工具長分割） | Zmap | 範囲全体で、工具長より上で接触するかを判定・分類する。パスほどの精度は要らない |
| 削り残しの領域の解析（工程設計・残り加工） | 後続 | Zmap | 製品形状と加工後の工作物の逆オフセット面を同じ格子で比べ、工作物の面が上にある範囲を取り出す（乾、2006）。範囲全体の分類で、使い回せる |
| 製品形状との比較（削り込みの確認） | #935・#1013 | 使わない | 切削シミュレーション（トリデクセル）と製品形状で比べる |

- 一定ピッチの Zmap は、容量があっても点の間の精度を保証できない（XY の格子では、急な壁で隣り合う点が上下に大きく離れて階段状の誤差になり、格子を細かくしても手間と記憶容量が増えるだけで解消しない。乾・崔、2002）。CL の面が不連続に変わる所（段差）をまたぐ 2 点の直線は、ピッチによらず段差の角を削り込み、ピッチより細い尾根は格子点の間に入ると見落とす。保証するには、点の間を確かめて細かくし、段差には段を入れる処理が要り、その処理があれば走査線の上では格子を前もって作る必要がない
- 範囲全体で Zmap を作る場合は、一定ピッチより先に、拡張 Z・map（郝・水垣・坂本、1994）を候補とする。格子を 4 分木で階層に分け、補間の誤差がトレランスを超える所だけを細かくし、領域ごとに最大・最小の高さを持って探索の範囲を絞る（#912 の打ち切りと同じ考え方）
- 拡張 Z・map の点の間の誤差の評価（中点で評価し、接触点が別の面へ飛ぶ所とフラットエンドミルは評価しない）は、12.4 の確かめ方の、仮定を置いた簡易版にあたる。本節では仮定を置かず、面が飛ぶ所も段として扱う

### 12.3 入力の役割

| 入力 | 役割 |
|---|---|
| ピックフィード | 走査線の間隔（工具径以下）。パスの間に残る山の高さは、平らな面のボールで r − √(r² − (s/2)²)（例: r = 5 mm、s = 2 mm で 0.10 mm）。条件として表示するだけで、制約にはしない（傾いた面では変わる） |
| トレランス（ツールパス生成） | CL の点を結ぶ経路が、CL の面からトレランスを超えて下を通らないことを保証する（12.4） |
| 送り・送り方・工具の移動範囲 | 9.8 のとおり（#994・#940） |

トレランス:

- 誤差は高さの向き（鉛直）で測る: 経路の各点で、経路の高さ ≥ CL の面の高さ − トレランス。面の法線の向きの誤差は、鉛直の誤差以下のため、鉛直で保証すれば法線の向きでも保証される（急な面では厳しすぎる側になる）
- 下側（削り込み）を保証する。上側（直線が CL の面より上を通る所。谷など）は削り残しの側のため保証せず、測る
- 誤差の配分: 形状のモデルの誤差 δ1（曲面を三角形に分ける弦の許容誤差 `chord_tolerance`）と、パスの誤差 δ2 の合計を、加工の公差 d 以下にする（d ≥ δ1 + δ2、δ1 ≤ δ2。郝・水垣・坂本、1994）。STL は三角形そのものが製品形状のため δ1 = 0 で、トレランスをすべてパスに使う。NURBS の配分の実装は後続（面から加工点と法線を直接求めて CL にすれば、三角形に分けずに δ1 = 0 にできる。樋野・社本・森脇、2003。ほかの面との干渉は別に扱う必要があり、比べて決める）

### 12.4 CL の点の並べ方

1. 走査線ごとに、工具の半径以下の等間隔で工具先端の高さ（`tip_height_at`）を求め、工具が形状に接する連続区間をパスとする。接する点と接しない点の間は二分し、パスの端をトレランスまで求める（12.9）
2. パスの隣り合う 2 点の区間ごとに、区間の XY にかかる要素を索引から集め、要素ごとに「区間の直線より上に出る量」の最大を、走査線の鉛直な平面で要素を切った形の式で求める。区間の両端も含める

   | 要素 | 走査線の鉛直な平面で切った形 | 最大の求め方 |
   |---|---|---|
   | 面・開いた形の上側の面 | 線分 | 区間の端（線分の端） |
   | ボールの頂点 | 球の断面の円 | 円の上で、直線との差が最大の点（閉じた式） |
   | ボールの辺 | 辺の長さの円柱の断面の楕円か、平行な 2 本の直線（軸への垂線の足が辺の中にある部分） | 曲線の上で直線との差が止まる点と、条件の境目（閉じた式） |
   | フラットの頂点 | 頂点の高さの水平な線分（円板の範囲） | 区間の端 |
   | フラットの辺 | 辺の上の位置 t を変数とする曲線 (x(t), z(t))（x(t) は円と辺の交点、z(t) は辺の高さ。x と t の平面の楕円） | 曲線の上で直線との差が止まる点と、t の端・区間の端（閉じた式） |

   頂点・辺の要素は範囲（隣り合う面ベクトルの間）で切らない。範囲の外の部分（球面・辺の長さの円柱面・円板の全体）も工具が形状に接する位置で、逆オフセット形状の内側にあり、上側の面より上に出ないため、最大は変わらない。要素は上限の高い順に調べ、それまでの最大が「要素の上限 − 弦の最も低い所」以上になった時点で打ち切る（8.11 の打ち切りと同じ）

3. 最大がトレランスを超えた区間は、その位置に点を足し（高さは `tip_height_at`）、2 つの区間で 2. を繰り返す。すべての要素を確かめるため、細い尾根も見落とさず、点が増えるのは必要な所だけになる
4. 区間の長さがトレランスより短くなっても超える所は、CL の面の段差（不連続）とする。高い側の端の高さのまま区間のもう一方の端まで進み、そこで下ろす（同じ XY に高さの違う 2 点を置く）。経路は CL の面より上にあり、削り込まない（削り残しは、水平にトレランス以下）
5. 区間の両端の点も式で確かめる。点の高さは鉛直線と要素の交点（`tip_height_at`）と、走査線の平面で切った式の 2 つの計算で確かめることになり、交点の計算の誤りで点が低く出ても、式の側で直せる
6. 上側（削り残し）は保証しない。CL の面の折れ点（2 つの要素の面が交わる所）は、走査線の断面では V 字の谷になり、谷をまたぐ直線は面より上を通る。上側を改善する場合は、隣り合う要素の断面の交点を折れ点として足す（乾・崔、2002 は、断面線の隣り合う 2 点の接線の向きが大きく違う所で、要素の式から求めた接線の交点を折れ点として加えた）
7. 間引き（直線で済む点を除く）は当面行わない。点を足すのはトレランスを超えた所だけのため、点の数を測ってから判断する（乾、2006 では、Zmap の格子点をつないだ折れ線を許容誤差 0.002 mm で間引き、多くの場合、線分が 10% 以下になった）

工具落ち（CL が CL の面より低くなり、工具が製品形状に食い込むこと）の危険:

| 危険 | Zmap（一定ピッチ） | 12.4 |
|---|---|---|
| 逆オフセット形状の誤り（要素の範囲の隙間、外しすぎ） | 同じ（点の高さは同じ要素から求める。8.11 のテストで抑える） | 同じ |
| 点の間の見落とし（細い尾根、段差） | ある | ない（すべての要素を式で確かめ、段差は段にする） |
| 点の高さの計算の誤り | 見つける手段がない | 式で確かめて直せる |
| 平面で切った形の式・最大の求め方の誤り | — | ある。要素の種類ごとに、総当たり（区間を細かく分けた `tip_height_at`）と比べるテストで確かめる |

### 12.5 確かめ方

- 要素の種類ごとに、区間の直線より上に出る量の最大が、区間を細かく分けて `tip_height_at` で求めた最大と一致する（円弧が平面に接する所、ほぼ平らな辺、範囲の境目を含む）
- 作った経路の細かい点で、経路の高さ ≥ CL の面の高さ − トレランス（尾根・谷・段差・張り出しのある形。ボール・フラット）
- サンプルデータで、#935 の比較で最も深い削り込みを測る（サンプル間隔 1 mm で 0.76 mm からの改善を見る。切削シミュレーションの精度の分を含む）。点の数・CL の大きさ・時間も測る

### 12.6 外すもの

- パスの間のエアカット・つなぎの移動（11 のとおり、後続）
- 上側（削り残し）の保証、間引き（12.4 の測定の後に判断）
- 等高線のパス、範囲全体の Zmap（12.2 のとおり、それぞれの工程で設計する）
- ラジアスエンドミル（平面で切った形がトーラス・オフセット円柱の断面になり、Newton 法が要る）
- NURBS の誤差の配分の実装（12.3）
- 加工点での送り速度の制御（送りは工具先端の速度とする。凹んだ所では加工点の送りが速くなり、凸の所では遅くなる。樋野・社本・森脇、2003 では、曲率の大きい所で約 1.5 倍）
- 大きな形状（例えば 4 m × 4 m）への対応（#1025）。CL の計算は面積ではなく点の数と形状の三角形の数に比例するため 12.4 の考え方は変えないが、候補を絞る索引の細かさ（升目は 1 辺 256 個までのため、大きな形状では 1 升が大きくなり候補が増える）、走査線ごとの並列計算、メモリが足りない場合に加工範囲を帯に分けて逆オフセット形状を作ること（帯の外の要素は工具の半径の分だけ含める）を、測ってから決める

### 12.7 実装の分け方

1. cam_algorithms: 区間の直線から、逆オフセット形状の要素が上に出る量の最大を求める（要素の種類ごとの、走査線の鉛直な平面で切った形の式と、区間にかかる要素の探索）
2. cam_algorithms: スキャン加工の CL の点を 1. で確かめて足し、段差を段にする。サンプルデータで、最も深い削り込み・点の数・時間を測る
3. viewmodel・view: パスの間に残る山の高さ（カスプハイト）を、加工条件のウィンドウに表示する

### 12.8 実装と測定（#1026・#1027）

- `InverseOffsetShape::rise_above_chord` が 12.4 の 2. を行い、`generate_scanline_toolpath` がパスごとに 3.〜5. を行う。トレランスはソルバーの入力の `chord_tolerance`（ツールパス生成のトレランス）とする。曲面の三角形への分割の誤差との配分（12.3）は後続のため、NURBS の入力では、三角形に分ける誤差とパスの誤差の合計が、最大でトレランスの 2 倍になる
- 点を足す位置は、区間の両端からトレランスの半分以上離す（分けた区間は必ず短くなり、繰り返しが終わる）。足す位置で工具が形状に接しない場合は、弦の上に置く
- 段の高さは、両端の高さと区間の中の最も高い所のうち最も高いものとする。最も高い所の高さは、`rise_above_chord` の値ではなく `tip_height_at` で求め直す（2 次曲線の計算に誤りがあっても、空中に高い段を作らない）

サンプルデータ（ボールエンドミル φ10、ピックフィード 2 mm、トレランス 0.001 mm、素材の精度 0.05 mm、release）:

| 項目 | サンプル間隔 1.0 mm（前 → 後） | サンプル間隔 0.25 mm（前 → 後） |
|---|---|---|
| 経路が CL の面より下を通る量の最大（経路を 0.02 mm ごとに分けた点） | 58.97 mm → 0.001 mm | 21.27 mm → 0.001 mm |
| 最も深い削り込み（切削シミュレーション） | 0.758 mm → 0.0008 mm | 0.194 mm → 0.0006 mm |
| 切削の線分の数（うち段の鉛直な線分） | 210,132 → 315,388（1,400） | 840,540 → 914,496（932） |
| ツールパスの計算の時間 | 0.28 s → 4.01 s | 0.88 s → 6.89 s |
| ジョブ全体の時間（切削シミュレーションを含む） | 6.97 s → 13.96 s | 26.84 s → 33.96 s |

- 前の「下を通る量」が大きいのは、急な壁をまたぐ 2 点の直線が壁の CL の面の下を通るため（切削シミュレーションでは、工具が壁の上の縁を削る量として現れる）
- サンプル間隔 1.0 mm で、0.25 mm の前より点が少なく、トレランスに収まる。点は必要な所にだけ増える

### 12.9 サンプル間隔を入力にしない（#1032）

12.4 の 2.〜4. で点の間を確かめるため、経路の誤差はサンプル間隔によらずトレランスに収まる。サンプル間隔は最初に置く点の数として時間と点の数に効くだけで、加工の条件として利用者が決める値ではないため、入力（`ScanlineParams`）から外し、内部で決める。

- サンプル間隔の影響が残るのは、工具が形状に接する区間（パス）の端だけになる。接する点と接しない点の間でパスを終えると、穴や形状の外形の所で、パスが本当の端よりサンプル間隔まで手前で終わり、削り残す（工具が通らないため、削り込みにはならない）。そのため、接する点と接しない点の間を二分し、接しない点からトレランス以内の接する点をパスの端に足す（1 か所に `tip_point_at` を約 log₂(間隔 ÷ トレランス) 回）
- 最初の点の並びの間隔は工具の半径以下とする（工具径の 10 mm より少し遅いが、小さな形状を見落としにくい側を選ぶ）。接しない区間の中にある小さな形状は、走査線に沿って接する長さが間隔より短いと見落とし、その所を削り残す（走査線の横に少しかかる形状）。見落としを減らす必要が出たら、間隔を細かくするか、接する区間の候補を索引から求める
- 間隔より短い接しない区間（狭い隙間・穴）は見落とし、両側の接する区間を 1 本のパスでつなぐ。2 点の間で接する・しないが何度か入れ替わる場合も、二分はそのうちの 1 つの境目を求め、同じようにつなぐ。つないだ区間も 12.4 の 2. で確かめるため、隙間の壁を削り込まない（隙間の上は弦の上を切削の送りで通る）。パスの間のエアカット・つなぎの移動（12.6）を入れるときに、隙間で分けるかを決める
