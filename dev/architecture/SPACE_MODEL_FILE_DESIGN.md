# 空間モデル（モデルファイル） 設計書

**作成日**: 2026年11月8日
**ステータス**: 設計中
**関連Issue**: #1068（本書）, #988, #933, #914, #1080

---

## 1. 目的

製品形状と、それに結び付ける加工手順・加工工程を、1 つの CAD の物理ファイル（モデルファイル。拡張子 `.rrm`）として保存・読み込みできるようにする。CAM の操作の画面では、加工プランのツリーの根をこの「空間モデル」とする（`CAM_OPERATION_UI_DESIGN.md` 3.1）。

## 2. 背景

- 今は、製品形状は Application の製品形状の保管先（`ProductShapeStore`）に、加工手順・加工工程は加工手順の保管先（`MachiningSequenceStore`）に、どちらもプロセスのメモリの中だけで持つ。アプリを閉じると失われる
- 面の ID（`FaceId`）・エンティティの ID（`EntityId`）・加工手順の ID（`MachiningSequenceId`）・加工工程の ID（`MachiningOperationId`）は、どれも作るたびにランダムな UUID（v4）とし、保存したものから作り直す手段がない。そのため、アプリを開き直すと、前に投入したジョブを工程から引けない（ジョブは投入元として、工程の ID と改訂の番号を持つ。`JOB_MANAGER_STORAGE_DESIGN.md` 4.4）
- 製品形状・加工手順の型は、ファイルに書き出す仕組みを持たない
- メニューの「ファイル」には「読み込み…」（STL の取り込み）だけがあり、保存も、保存していない変更の記録もない
- 取り込んだ CL は空間モデルに一方向に写し、NC の出力・受け渡しはモデルファイルだけで済むようにする方針がある（`JOB_MANAGER_STORAGE_DESIGN.md` 6 章）

## 3. 空間モデルが持つもの・持たないもの

| 持つもの | 内容 |
|---|---|
| 空間モデルの情報 | 空間モデルの ID（UUID）、保存したプログラムの版、保存した時刻 |
| 製品形状の面 | 面ごとに、面の ID・エンティティの ID・形状（メッシュ、または NURBS の曲面）・表示の属性（色・線の種類・線の太さ・レイヤー・見えるか）・エンティティの属性とメタデータ。補助面・型の形状など、加工に関係ない面も含む |
| 加工手順・加工工程 | 加工手順の ID・名前・加工の対象の面の ID・素材（素材の余裕・精度）。加工工程の ID・改訂の番号・改訂の鍵（5 章）・中身（名前・加工の段階・加工の方式と条件・工具・加工領域・トレランス） |
| 取り込んだ CL（後で足す） | 工程ごとに 1 つ（`JOB_MANAGER_STORAGE_DESIGN.md` 6 章）。もとにした工程の ID と改訂の鍵を添える。区画の種類だけを決め、CL の取り込み（#1080）と合わせて足す |
| フィーチャー（後で足す） | 名前と種類を付けた、空間モデルの面の ID の集まり（10 章） |

| 持たないもの | 理由 |
|---|---|
| ジョブ・ジョブの入力・成果物 | ジョブマネージャーが持つ。空間モデルは、工程の ID と改訂の鍵でジョブを引き直す（9 章） |
| 表示用に分割した三角形 | 形状から毎回作る |
| 選択の状態・画面の配置・カメラ | 作業の途中の状態で、空間モデルの内容ではない |
| アプリの設定（言語など） | アプリの設定のファイルに置く |

## 4. ファイルの形式

### 4.1 全体

成果物・ジョブの入力と同じ共通のヘッダ（`ARTIFACT_BINARY_IO_CONTRACT_DESIGN.md`）を使い、種類 `RRMF` を足す。単位（mm）・座標系（右手系・Z が上）・リトルエンディアン・信用できない入力としての読み方は、成果物と同じとする。

ヘッダの後の中身は、区画を並べたものとする。

```text
共通のヘッダ（種類 RRMF）
区画の数        u32
区画 × 区画の数
  区画の種類    [u8; 4]
  区画の版      u16
  区画の印      u16      bit0: 必須（読む側が知らなければ、開かない）
  区画の長さ    u64
  区画の中身    [u8; 区画の長さ]
```

| 区画の種類 | 中身 | 必須 |
|---|---|---|
| `INFO` | 空間モデルの情報（空間モデルの ID・保存したプログラムの版・保存した時刻） | はい |
| `FACE` | 製品形状の面の列（形状は、今の製品形状の面の 2 種類（メッシュ・NURBS の曲面）を書く） | はい |
| `MSEQ` | 加工手順・加工工程の列 | はい |
| `CLDT`（後で足す） | 工程ごとの取り込んだ CL（もとにした工程の ID と改訂の鍵を添える） | いいえ |
| `FEAT`（後で足す） | フィーチャーの列 | はい |

- 区画の中身のバイトの並び（面の形状・工具などの書き方）は、実装の Issue（12 章）で決め、成果物と同じくゴールデンのバイト列の試験を置く
- ほかの区画から参照される区画（空間モデルの情報・面・加工手順・フィーチャー）は、必須とする。読む側が知らない必須の区画があれば、開かずに理由を出す（参照の先を落としたまま開かない）
- 読む側が知らない必須でない区画は、そのままのバイト列で持ち、保存のときにそのまま書き戻す（新しい版で書いたファイルを古い版で開いて保存しても、知らない内容を失わない）
- 必須でない区画がほかの区画を参照するときは、参照の先を ID と改訂の鍵で持つ。古い版が参照の先を変えて書き戻しても、新しい版は鍵の違いで古くなったと分かる（例: `CLDT` は、もとにした工程の改訂の鍵と今の鍵が違えば、取り込み直しが要ると示す）

### 4.2 版の扱い

- 共通のヘッダの版は、すべての種類で共有する（どの種類の中身を変えても、小さい版の番号が上がる。`ARTIFACT_BINARY_IO_CONTRACT_DESIGN.md`）。モデルファイルは、成果物と同じく、知っている小さい版の番号をすべて受け入れる（ほかの種類の変更で版の番号が上がっても、前に保存したモデルファイルを開ける）
- 空間モデルの中身の変更は、区画の版で表す。区画に項目を足す変更は、区画の版を上げ、古い版の区画も読めるようにする。読めない版の必須の区画があれば、開かずに理由を出す
- 新しい区画を足す変更は、区画の種類を足すだけで済む

## 5. ID の保ち方

- 面の ID・エンティティの ID・加工手順の ID・加工工程の ID・空間モデルの ID は、UUID の 16 バイトをそのまま保存し、読み込みで同じ ID に戻す。改訂の番号と改訂の鍵も保存する
- ID の型に、UUID から作る作り方を足す（ID の型と保管先はクレートが違うため、公開の作り方になる）。保管先は、保存したものから戻す口で、戻す中身をまとめて検証する
- 読み込みのときに、次を検証し、満たさなければ開かずに理由を出す
  - 同じ種類の ID が重なっていない（面の ID、エンティティの ID、加工手順の ID、加工工程の ID）
  - 加工手順の加工の対象の面の ID が重なっていない
  - 加工工程の改訂の番号が 1 以上
- 新しく作る面・加工手順・加工工程は、これまでどおりランダムな UUID とする

### 5.1 改訂の鍵

改訂の番号だけでは、別々の中身に同じ番号が付くことがある。

- モデルファイルを複製し、それぞれで条件を変えると、どちらも同じ工程の ID・同じ改訂の番号になる
- 条件を変えて投入し、保存せずに閉じてから開き直すと、改訂の番号が戻る。そこで別の条件に変えると、前に捨てた変更と同じ改訂の番号になる

どちらの場合も、工程の ID と改訂の番号でジョブを引くと、違う中身から計算したジョブに結び付いてしまう。そこで、加工工程は、改訂の番号を上げるたびに新しいランダムな UUID（改訂の鍵）を持つ。

- 改訂の鍵は、改訂の番号と同じときに作り直し（条件・加工の対象・素材を変えたとき）、モデルファイルに保存する
- ジョブの投入元は、工程の ID と改訂の番号に、改訂の鍵を足す（ジョブの記録の投入元に項目を足す。前の版の記録は鍵を持たないため、鍵のない記録は今の改訂のジョブとみなさない）
- ジョブを引くときは、工程の ID と改訂の鍵で引く。改訂の番号は、画面に出す・人が見分けるために残す
- 新しく作る面・加工手順・加工工程は、これまでどおりランダムな UUID とする

## 6. 取り込み・開く・新規

1 つのアプリのウィンドウで、1 つの空間モデルだけを扱う（SDI）。最終の目標は、1 つのウィンドウでタブを切り替えて複数の空間モデルを扱う形（MDI）とし、それまでは SDI の最小限にとどめる。

- MDI に移りやすいように、空間モデルに関わる状態（製品形状・加工手順・加工工程・開いたファイル・保存していない変更）は、実装で 1 つのまとまり（文書）に集める。MDI では、このまとまりを複数持つ
- アプリを 2 つ以上起動することは止めないが、そのための仕組みは作らない。同じモデルファイルを 2 つのアプリで開いて両方で保存すると、後から保存したほうが残る（制約。同じファイルを二重に開かない決まりは、同じプロセスの中のタブになる MDI で入れる）
- 新しいウィンドウで開く動きは作らない

| 操作 | 動き |
|---|---|
| 新規 | 空の空間モデルにする（加工手順・加工工程は、今と同じく既定の 1 つずつを作る） |
| 開く | モデルファイルを読み、今の空間モデルを置き換える |
| 読み込み（STL の取り込み） | 今の空間モデルに面を加える（新しい面の ID を作る）。空間モデルは置き換えない |

- 取り込み元のファイルの名前・要素の番号は、今は持たない（`PRODUCT_SHAPE_ENTITY_DESIGN.md` 7 の「取り込み元の要素の番号を残すか」は、段階 2 で決める）

## 7. 面を変えた・消したときの、加工の対象の参照

- 加工手順の加工の対象は、面の ID で参照する（`PRODUCT_SHAPE_ENTITY_DESIGN.md` 3.4）。参照の先の面がなくなっても、参照は勝手に消さずに残す
- 参照の先の面がない加工手順は、誤りとして示し、投入できなくする（`CAM_PROCESS_ENTITY_DESIGN.md` の参照が切れたときの決め事のとおり）。読み込みのときも同じに扱い、開くことはやめない
- 面の分割・まとめで ID を引き継ぐ決まり（`PRODUCT_SHAPE_ENTITY_DESIGN.md` 7）は、段階 2 で決める。それまで、面を消す操作は持たない

## 8. 保存の操作

- メニューの「ファイル」を、次の項目にする

| 項目 | キー | 動き |
|---|---|---|
| 新規 | Ctrl+N | 6 章 |
| 開く… | Ctrl+O | ファイルを選んで開く（6 章） |
| 保存 | Ctrl+S | 開いたファイル・前に保存したファイルに書く。まだなければ、名前を付けて保存と同じ |
| 名前を付けて保存… | Ctrl+Shift+S | ファイルを選んで書く |
| 読み込み… | （今のまま） | STL を取り込む（6 章） |
| 終了 | （なし） | アプリを終える |

- ウィンドウにファイルを落としたときは、モデルファイルは「開く」と同じに扱い（今の空間モデルを置き換える）、STL は「読み込み」と同じに扱う（今の空間モデルに面を加える）
- 保存は、一時の名前で書き終えてから名前を変える（書きかけのファイルを残さない）
- 保存していない変更を記録する。変更は、空間モデルに保存する内容（3 章）を変える操作すべてとする（面の取り込み・面の表示の切り替え、加工手順・加工工程の追加と、名前・加工の対象・素材・条件の変更）。開く・保存・新規で、変更なしに戻す
- 保存していない変更があるときに、新規・開く・アプリを閉じる操作（終了・ウィンドウを閉じる・キーでアプリを終える）をしたら、「保存する／保存しない／やめる」を確かめる
- 今のキー操作は、Shift などとの組み合わせを見分けずに文字のキーで決めている（例: Shift+S）。Ctrl との組み合わせを足すときは、組み合わせを見分けるようにし、Ctrl+Shift+S で Shift+S の操作が動かないようにする
- ウィンドウの題に、ファイルの名前と、保存していない変更があることを出す
- 画面の文言は、キー・メニューの名前を出さない一般的なものとし、具体的な手順はマニュアルに書く

## 9. ジョブとの結び付き

- 工程の ID と改訂の鍵を保つため、開き直した後も、「工程の今の改訂のジョブを引く」仕組み（`CamSimulationWorkflow::latest_revision_job_status`・取り込み）で、前に投入したジョブに結び付く（引き方を、改訂の番号から改訂の鍵に替える。5.1）
- 同じモデルファイルを複製して別の名前で保存すると、同じ工程の ID を持つ空間モデルが 2 つになる。どちらかで条件を変えるまでは同じ改訂の鍵を持つため、同じ中身のジョブとして、どちらからも見える。条件を変えた後の投入は、改訂の鍵で区別できる。複製をジョブの一覧で区別する（ジョブに空間モデルの ID を持たせる）のは、ジョブマネージャーの空間モデルごとの絞り込み（`CAM_OPERATION_UI_DESIGN.md` 3.7）と合わせて決める
- ジョブ・成果物はジョブマネージャーが持つため、ジョブの保存先から消えたジョブは、開き直しても取り込めない。取り込んだ CL を空間モデルに写す（`CLDT`）までは、取り込みにジョブの成果物が要る

## 10. フィーチャー

- 最初の版には入れない。CAM の操作の画面の「フィーチャー」タブ（`CAM_OPERATION_UI_DESIGN.md` 3.8）と合わせて、段階 3 で足す
- 足すときは、名前と種類を付けた面の ID の集まりを、区画 `FEAT`（必須）に置く。工程の加工の対象・加工領域からフィーチャーへの参照は、フィーチャーの ID（UUID）で行い、区画 `MSEQ` の版を上げて足す

## 11. 読み込みの安全

モデルファイルは、ほかの人から渡されうるため、信用できない入力として読む（`ARTIFACT_BINARY_IO_CONTRACT_DESIGN.md` の決まりのとおり）。

- 区画の長さ・区画の中の数（面の数・頂点の数・工程の数など）は、ファイルの残りのバイト数で上限を確かめてから読む。先に確保する大きさにも上限を置く
- 区画は、区画の長さのバイト数をちょうど読み終える。足りない・余るときは誤りにする
- 壊れたファイルで落ちない。壊したバイト列の試験を置く
- ファイルの大きさの上限を置く（実装の Issue で決める）

## 12. 実装の段階と Issue

| 段階 | 内容 | 依存 |
|---|---|---|
| 1 | ID を UUID から作る作り方と改訂の鍵（5 章）、ジョブの投入元に改訂の鍵を足して鍵で引く（5.1・9 章）、製品形状・加工手順の保管先の中身を取り出す・戻す口 | ― |
| 2 | モデルファイルの読み書き（4 章・11 章。区画 `INFO`・`FACE`・`MSEQ`）。共通のヘッダに種類 `RRMF` を足す | 段階 1 |
| 3 | 「ファイル」のメニュー（新規・開く・保存・名前を付けて保存）、キーの組み合わせの見分け、保存していない変更の確かめ（8 章） | 段階 2 |
| 4 | 取り込んだ CL の区画 `CLDT` | 段階 2、#1080 |
| 5 | フィーチャーの区画 `FEAT` | 段階 2、`CAM_OPERATION_UI_DESIGN.md` 段階 3 |

- 読み書きを新しいクレートに置く場合は、依存の決まり（`scripts/_arch_rules_data.ps1`）の変更になるため、実装の Issue で確かめてから行う

## 13. 決めていないこと

- 区画の中身のバイトの並びと、ファイルの大きさの上限（段階 2）
- 複製した空間モデルとジョブの区別（9 章）
- 最近開いたファイルの一覧、自動の保存
- MDI（タブ）の画面と、同じファイルを二重に開かない決まり（6 章）
- 起動の引数でモデルファイルを受け取ること（ファイルの関連付け。配布の形を決めるときに合わせる）
