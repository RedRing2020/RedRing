# UI フレームワーク選定メモ

最終更新: 2026年3月31日

## 選定結論: egui 一択

RedRing（winit + wgpu 構成）に対してメニューボタン等の GUI を追加する場合、  
フレームワークは **egui**（`egui-wgpu` クレート経由）を採用する。

## 理由

| 候補 | 評価 |
|---|---|
| **egui** | `egui-wgpu` で wgpu バックエンドに直接統合可能。winit との組み合わせ実績多数。**採用** |
| imgui-rs | デバッグ用途寄り。C ライブラリバインディングでメンテコストが高い |
| iced | 独自イベントループで winit との統合が複雑 |

## 統合時の想定工数

| 作業 | 工数 |
|---|---|
| egui-wgpu 統合・描画パイプライン接続 | 1〜2日 |
| winit イベントループへの egui 入力転送 | 半日 |
| 基本メニューバー実装 | 半日〜1日 |
| **合計** | **2〜4日** |

## 統合ポイント

- wgpu のレンダーパスに egui を**後段**で合成する構造変更が必要
- 影響範囲: `app_renderer.rs` 周辺
- winit の `WindowEvent` を `egui_winit::State` に転送し、egui 側のスクリーン座標系と wgpu の座標系を合わせる

## 実施タイミング

`h` キーのログ表示で代替できている現状（Series A デモ改善フェーズ）では不要。  
Series B 以降の「本格的な操作 GUI が必要な機能」追加時に実施する。

## 2026年3月31日時点の実装方針

Series A の切削シミュレーションデモ改善に限り、`view/app` へ **最小の egui 設定パネル** を導入する。

### 目的

- 「設定値はあるが設定画面がない」状態を解消する
- 既存の保持値をユーザーが画面上で確認できるようにする
- 工具ワイヤーフレーム分割数を実行中に調整できるようにする

### 今回のスコープ

- 画面右上に固定表示する最小パネル
- 開閉トグルのみを持つ簡易運用
- 以下の設定カテゴリを一覧表示
	- View 操作設定
	- Octree 可視化設定
	- Snapshot Overlay 設定
	- Snapshot Shading 設定
	- Tool Wireframe 設定
- Tool Wireframe 設定のみ編集可能
	- flat 円周分割数
	- ball 円周分割数
	- ball 半球緯線分割数
	- ball 半球経線本数

### 非スコープ

- 汎用設定システム化
- 永続化
- 全設定の編集UI化
- ドッキングUIやメニューバー整備

### 実装境界

- GUI 実装は `view/app` に閉じる
- 工具ワイヤーフレーム設定の型は `viewmodel/converter` に置き、可視化変換関数へ明示注入する
- `cam_core` / `cam_sim` には GUI 依存を持ち込まない
